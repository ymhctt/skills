# 项目进展汇报

帮助你将零散的工作记录整理成清晰、专业的进展汇报，适合发给领导、在群里同步、或站会时使用。

## 前置条件

无。本技能不需要任何 CLI 工具或外部依赖。只需用户提供工作内容即可。

如果用户有维护项目待办文件（如 `TODO.md`、`issues.md`、或项目看板导出），可以一并读取来增强汇报的完整性和准确性。

## 执行流程

### Step 1: 确定汇报模式

根据用户意图判断模式：

| 模式 | 触发词 | 适用场景 |
|------|--------|---------|
| **日报** | 日报、今天、今日、daily、下班 | 每天下班前的简短汇报 |
| **周报** | 周报、本周、这周、weekly | 每周一次的全面回顾 |
| **自定义** | 指定时间范围 | 阶段性汇报 |

如果用户没有明确说明，主动询问。

### Step 2: 收集工作内容

按优先级尝试以下方式：

1. **用户口述**（主要方式）— 用户直接描述今天/本周做了什么。可以分多次输入，技能负责整理汇总。
2. **待办文件**（辅助方式）— 如果用户提到了项目待办文件（如 `TODO.md`、`issues.md`），读取并提取相关条目：
   - 已完成的事项 → 归入「完成工作」
   - 进行中的事项 → 归入「进行中」或「遗留」
   - 标记为阻塞的事项 → 归入「需要协调」

读取待办文件时，关注近期的更新和状态变更，而非全量罗列。

3. **补充追问** — 收集完基础信息后，针对以下维度主动查漏补缺：
   - 有没有昨天/上周遗留的工作今天处理了？
   - 有没有遇到需要别人配合才能推进的阻塞？
   - 有没有计划中的工作没有完成？原因是什么？
   - 明天/下周的优先级是什么？

### Step 3: 内容完整性检查（关键步骤）

在整理汇报之前，先审视用户提供的信息是否完整。**你的角色不仅是记录者，更是思考伙伴**——帮汇报者发现遗漏、提醒补充关键信息，让汇报更有分量。

逐项对照以下清单，发现缺口时主动向用户提问：

**时间维度：**
- 每项完成的工作是否知道完成时间？有没有 deadline 或里程碑节点？
- 进行中的工作有没有预计完成时间？如果延期了，新的时间点是什么？
- 待办事项有没有处理时限？（如「需在 6/28 前审批通过」）
- 阻塞了多久？（如「已提单 3 天未处理」更能引起重视）

**责任人维度：**
- 需要协调的事项是否明确了谁在负责推进？
- 阻塞项是否有具体的对接人或依赖方？
- 下一步计划是否需要指定负责人？

**信息完整度：**
- 用户描述是否过于简略？是否需要补充背景让读者理解上下文？
- 成就是否可以量化？（时间节省了多少、性能提升多少、覆盖多少用户）
- 风险/problems 是否说明了影响范围？
- 有没有本该完成但未提及的工作？（对比上次汇报或待办文件）

**优先级判断：**
- 用户提到的事项是否有轻重缓急？哪些是今天最重要的产出？
- 是否有紧急但用户轻描淡写的内容值得重点标注？

**提问方式：**
不要一次性抛出所有问题轰炸用户。遵循「先整理、再追问」的节奏：
1. 先将已有的信息整理成草稿
2. 标注出信息缺失的地方
3. 用简短的 2-3 个问题引导用户补充
4. 用户补充后，更新草稿

向用户提问时，用具体的提示而非泛泛的「还有吗」。例如：
- 「DM TOPSQL 这个问题有处理 deadline 吗？陆老师有没有给时间要求？」
- 「连接池调整预计什么时候能改完上线？」
- 「TOPSQL 问题的跟进，需要我帮你 @哪位同事？」

### Step 4: 整理汇报内容

将收集到的信息按以下结构组织。**每项工作有已知的时间节点或 deadline 时，必须标注。**

```
## 汇报结构

### 1. 今日完成
- 列出今天/本周已完成的事项
- 优先写有结果的工作，而非过程描述
- 每项一句话，有完成时间或里程碑节点时注明

### 2. 进行中
- 列出已开始但未完成的工作
- 说明当前进度和预计完成时间（必填）
- 有 deadline 的标注：「预计 6/28 完成，需在 6/30 前上线」

### 3. 待办事项（如果有）
- 需要他人配合的事项、需要领导决策或关注的风险
- 从之前汇报中遗留的待办
- 标注处理时限、已等待时长、责任人
- 这一节可以留空（如果确实没有），但必须要问过用户

### 4. 下一步计划
- 明天/下周的优先级安排
- 如有时间节点一并标注
- 日报写 2-3 项，周报写 3-5 项
```

### Step 5: 输出

默认输出**简洁要点式**（适合微信、钉钉、站会口述）：

```
## <项目名> <日期/周> 进展汇报

### 【今日完成】
- 完成了用户登录模块的接口联调
- 修复了首页加载慢的问题，首屏时间从 3s 降到 0.8s
- 上线了合同报表导出功能（按计划 6/24 上线）

### 【进行中】
- 权限管理重构：后端接口已完成，前端预计 6/25 完成，目标 6/28 提测
- 数据看板：等待设计稿确认（依赖产品侧，预计 6/26 交付）

### 【待办事项】
- 文件上传功能需要运维开通 OSS 权限，已提单 2 天未处理，阻塞上传联调

### 【下一步】
- 6/25：权限管理重构收尾 + 提测
- 6/26：开始数据看板的前端开发
- 本周内：处理上周遗留的导出格式兼容问题
```

如果用户要求**正式书面版本**（适合邮件或正式文档），则展开为完整段落，增加背景说明和影响分析。

## 风格指南

### 写作原则

1. **先结果后过程** — 每项先说结论/结果，再说怎么做的。领导关心的是「交付了什么」，不是「做了什么事」。
   - 避免：「花了一天时间调试登录接口的跨域问题」
   - 推荐：「解决了登录接口的跨域问题，已正常联调通过」

2. **量化优先** — 能用数字描述的尽量用数字（时间、比例、数量）。
   - 避免：「优化了页面加载速度」
   - 推荐：「页面首屏加载时间从 3s 降到 0.8s」

3. **重点突出** — 日报控制在 10 项以内。不是流水账，挑选重要的事情写。
4. **诚实直接** — 没完成就是没完成，不需要粉饰，但要说明原因和下一步计划。
5. **中文为主** — 技术名词保留英文，其余用中文。

### 长度控制

| 模式 | 推荐长度 |
|------|---------|
| 日报 | 5-10 个要点，总字数 150-300 字 |
| 周报 | 8-15 个要点，总字数 300-500 字 |
| 正式版 | 根据内容自然展开，段落形式 |

## 待办追踪（跨会话记忆）

为了让汇报在多次会话中保持连贯，维护一个轻量的待办追踪文件：

**文件位置**：`skills/pm/pm-progress-report/references/tasks.json`

**结构**：
```json
{
  "last_updated": "2026-06-24",
  "items": [
    {
      "id": "1",
      "title": "权限管理重构",
      "status": "in_progress",
      "created": "2026-06-20",
      "notes": "后端接口完成，前端预计 6/25 完成"
    }
  ]
}
```

**使用方式**：
- 每次汇报结束后，更新 `tasks.json`：已完成 → `done`，新增 → `todo`/`in_progress`
- 下一次汇报时，先读取 `tasks.json`，将进行中和未开始的待办纳入「待办回顾」区域
- 超过 2 周未更新的已完成项自动清理

**这是一项可选功能**。如果用户没有维护待办文件的需求，可以跳过。用户可以手工编辑 `tasks.json` 来管理自己的待办列表。

## 注意事项

- **主动追问阻塞项**：用户容易忘记提需要协调的事项，技能应主动询问。
- **区分日报和周报的粒度**：日报聚焦当天的具体产出，周报侧重本周的整体进展和趋势。
- **待办回顾要具体**：不说「处理中」，而说「接口开发完成 80%，剩余 2 个接口预计明天完成」。
- **没有进展也是进展**：如果某待办没有推进，诚实说明原因（等待依赖、优先级调整等），比沉默不写更好。
