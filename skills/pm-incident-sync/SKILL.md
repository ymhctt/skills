# 故障信息同步

帮助你将故障处理过程中零散的信息整理成清晰、完整的同步消息，确保团队和领导快速了解故障全貌和当前状态。

## 前置条件

无。本技能不需要任何 CLI 工具或外部依赖。

如果后续需要通过 MES 创建事件个案，需确保 MES CLI 已安装并已认证（`mes auth status`）。

## 执行流程

### Step 1: 收集故障信息

逐项向用户收集以下关键信息。**不要一次性抛出所有问题**，按自然对话节奏逐步获取。

#### 必填项

| 项目 | 说明 | 示例 |
|------|------|------|
| **故障现象** | 发生了什么？用户/系统看到了什么？ | 「业务系统登录页面报 502 错误，用户无法登录」 |
| **影响程度** | 影响范围和业务影响 | 「影响核心业务系统，所有用户无法登录」或「仅影响管理后台，核心业务正常」 |
| **故障发生时间** | 何时开始 | 「6/24 14:30 左右开始」或「14:30 监控告警首次触发」 |
| **当前状态** | 故障是否仍在持续 | 「持续中」「已恢复」「间歇性」 |

#### 选填项（有则必填）

| 项目 | 说明 |
|------|------|
| **已执行操作** | 截至目前已经做了哪些处理（重启、回滚、切流、扩缩容等） |
| **初步原因** | 当前判断的根因或排查方向（不确定也要写，标明「初步判断」） |
| **下一步计划** | 接下来准备做什么、谁在做 |

### Step 2: 影响程度判断

帮助用户准确描述影响程度，这是领导最关心的信息。按以下分级：

| 级别 | 描述 | 关键词 |
|------|------|--------|
| **P0 严重** | 核心业务完全不可用，涉及所有用户或大面积用户 | 全部不可用、系统崩溃、数据丢失 |
| **P1 高** | 核心功能受影响但未完全中断，或影响部分用户 | 部分用户、功能降级、性能严重下降 |
| **P2 中** | 非核心功能异常，不影响主业务流程 | 管理后台、报表、辅助功能 |
| **P3 低** | 偶发报错、仅日志告警、对业务无实际影响 | 日志报错、偶发、无业务影响 |

如果用户描述模糊（如「系统有问题」），主动追问以确定级别。

### Step 3: 内容完整性检查

整理草稿后，审视是否有以下遗漏：

- 故障持续了多久？（从发生到现在的时间跨度）
- 是否通知了相关方？（领导、客户、业务方）
- 是否有监控截图或日志片段可以引用？
- 排查的人是谁？是否需要协调其他人？
- 如果故障已恢复，恢复时间是什么？恢复方式是什么？
- 是否需要对客户或业务方发送对外口径的通报？

### Step 4: 输出

按以下格式输出同步消息：

```
## <项目/系统名> 故障同步 — <日期> <时间>

### 故障现象
<描述具体现象>

### 影响程度
【P1 高】影响核心业务系统登录功能，所有用户无法登录
# 或
【P3 低】仅业务日志偶发报错，对核心业务系统无实际影响

### 发生时间
6/24 14:30 左右开始，持续至今（约 30 分钟）
# 如果已恢复：
6/24 14:30 发生，14:50 恢复（持续约 20 分钟）

### 已执行操作
- 14:32 确认告警，开始排查
- 14:35 检查应用日志，发现数据库连接超时
- 14:40 确认数据库侧正常，定位到连接池配置问题
- 14:48 调整连接池参数并重启应用服务

### 初步原因（如果有）
初步判断为连接池空闲连接未主动释放，数据库侧超时断开后应用未及时感知，
导致部分请求使用了已断开的连接。根因仍在排查中。

### 下一步
- <责任人> 继续排查根因，确认是否需要调整数据库超时参数
- <责任人> 评估是否需要增加连接池健康检查机制
- 持续监控 30 分钟确认不再复发
```

### Step 5: MES 事件个案（可选）

如果用户需要创建 MES 事件个案以留档追踪，操作路径为：

> **注意**：需先确认 MES CLI 当前版本是否支持事件个案创建命令。
> 如支持，参考以下流程；如不支持，提示用户通过 MES Web 界面手动创建。

```bash
# 确认 MES 登录状态
mes auth status

# 如果 CLI 支持事件个案创建（具体命令以实际版本为准）：
mes incident create \
  --title "<故障简述>" \
  --level <P0|P1|P2|P3> \
  --occurred-at "<发生时间>" \
  --description "<故障详情>"
```

如果 MES CLI 当前不支持此命令，告知用户通过 Web 界面创建，并提供整理好的故障描述文本供直接粘贴。

## 风格指南

1. **时间线清晰** — 故障同步的核心是时间线。每个操作标注时间点，让读者一眼看懂事件演进。
2. **先结论后细节** — 开头用一句话说明当前状态：「故障已恢复」或「故障持续中，正在排查」。
3. **影响程度先说** — 领导最关心「严不严重」，影响程度放在最前面或紧随标题之后。
4. **不确定就说「不确定」** — 原因分析阶段，诚实比猜测更重要。用「初步判断」「待确认」「可能」等措辞。
5. **避免技术黑话** — 考虑非技术领导的阅读体验，用业务影响而非技术细节描述问题。
   - 避免：「Kubernetes集群的CNI插件出现pod网络隔离异常」
   - 推荐：「容器网络异常导致服务间调用失败，影响用户登录」
6. **恢复后做总结** — 故障恢复后，建议补充一条总结消息，包含根因、影响时长、改进措施。

## 多次同步场景

故障处理过程中可能需要多次同步信息（初报、进展更新、恢复通知）。识别当前所处的阶段：

| 阶段 | 侧重点 | 典型标题 |
|------|--------|---------|
| **初报** | 现象 + 影响 + 谁在处理 | 「故障同步」 |
| **进展更新** | 排查进展 + 新发现 + 预计恢复时间 | 「故障进展更新」 |
| **恢复通知** | 恢复时间 + 原因 + 影响时长 | 「故障恢复通知」 |

进展更新时，在原有内容基础上追加，不用重复已同步过的信息。格式上只需列出新进展即可：

```
## 故障进展更新 — 6/24 15:10

- 15:05 已定位根因：数据库连接池配置 maxIdle 参数与外部队列超时不匹配
- 15:08 完成连接池参数调整，重启应用
- 15:10 服务恢复正常，持续监控中
- 预计 15:40 确认稳定后发送恢复通知
```
