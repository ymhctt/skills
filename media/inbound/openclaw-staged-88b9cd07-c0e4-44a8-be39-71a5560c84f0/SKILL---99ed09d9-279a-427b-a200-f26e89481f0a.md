# MES 智能报工技能

## 功能说明

本技能的**最终目标是向 MES 提交报工**。用户输入自然语言描述的工作内容，技能会：

1. 自动识别工作大类（五类）
2. 按对应报工模板的章节结构，把内容组织成结构化报工备注（remark）
3. **提交到 MES 系统**完成报工

《服务类的报工模版》《实施交付类报工模版》两份标准文档用于界定部分工作的**内容结构**，是 remark 组织的依据——**不是**最终产出物。仅当用户明确要求（"顺便生成 word / 输出文档留存"）时，才额外输出一份 `.docx`。

### 核心能力

1. **自然语言转报工（主路径）**：自然语言 → 识别工作大类 → 结构化 remark → **提交 MES**
2. **五类工作自动识别**：服务类-故障分析 / 服务类-主动计划 / 实施交付类 / 会议类 / 验收与报告编写类
3. **模板化章节组织**：按 框架A（服务类）/ 框架B（实施交付类）/ 框架C（会议类）/ 框架D（验收与报告编写类）组织 remark
4. **批量报工**：多天 / 多事项 → 拆分 → 逐条提交
5. **量化数据提取**：自动提取检查X套、耗时X分钟、优化X% 等指标
6. **合规校验**：工时上限（10h/日）、remark 长度、时间格式、不跨天
7. **（可选）Word 留存**：仅当用户明确要求时才额外输出 .docx，不改变主流程

## 五类工作识别（核心）

服务类 / 实施交付类 提炼自两份标准报工模板；会议类、验收与报告编写类 为新增通用工作类型。

| 大类 | 子场景 | 判定关键词（命中即归此类） | 套用框架 |
|------|--------|------------------------------|----------|
| **服务类** | 故障分析 | 故障、hang起/夯住、异常、告警、客户报障、原因定位、排查、恢复、根因 | 框架A |
| **服务类** | 主动计划 | 巡检、计划内、定期、健康巡检、主动服务、安装部署(主动)、优化(主动)、定期复盘 | 框架A |
| **实施交付类** | — | 项目阶段、实施调试、一体机/设备到货、上架、进展说明、交付里程碑、当前阶段 | 框架B |
| **会议类** | — | 会议、开会、例会、周会、日会、评审会、沟通会、研讨会、专题会、站会、复盘会、汇报会 | 框架C |
| **验收与报告编写类** | — | 验收、报告编写、编写报告、撰写、编制文档、输出文档、材料编写、文档产出、验收材料、编写方案、编制总结 | 框架D |

**识别优先级与规则**（自上而下，命中即停）：

1. 先判**会议类**：命中"会议/开会/例会/周会/评审会/沟通会/研讨会/专题会/站会/复盘会/汇报会"等词 → 框架C。
2. 再判**验收与报告编写类**：命中"验收/报告编写/编写报告/撰写/编制文档/输出文档/材料编写/文档产出/验收材料/编写方案/编制总结"等词 → 框架D。
3. 再判**实施交付类**：命中"项目/阶段/交付/实施/里程碑/上架/到货/进展说明"等词 → 框架B。
4. 否则判**服务类**，并区分子场景：
   - 命中"故障/异常/排查/根因/hang起/告警/报障" → **故障分析**
   - 否则（巡检/计划内/主动工作/安装部署等） → **主动计划**
5. 均不命中 → 默认**服务类-主动计划**，或追问用户「这属于哪类工作（服务-故障 / 服务-计划 / 实施交付 / 会议 / 验收报告）？」

## 报工模板章节（remark 结构）

**框架A — 服务类（故障分析 / 主动计划 共用章节，内容侧重不同）**

```
【工作情况】
  1）、<针对某项服务请求的具体响应/计划工作项>
  2）、...
【客户反馈】
  1）、<客户对服务的反馈、闭环状态、待确认事项>
  2）、...（无则填"无"）
【待办计划】
  1）、<后续工作项>
  2）、...（无则填"无"）
【协调事项】
  1）、<需协调客户/二线/产研的事项>
  2）、...（无则填"无"）
【风险提示】
  1）、<与客户沟通或执行中暴露的风险>
  2）、...（无则填"无"）
```

> 故障分析侧重：处置 → 分析原因 → 编制报告 → 汇报；客户反馈多为"已闭环/需X日提交报告"；协调事项多为"协调二线/客户提供日志"。
> 主动计划侧重：巡检数据 → 分析 → 编制报告 → 汇报/安装部署；客户反馈多为"已闭环/需整改"；协调事项多为"协调客户提供数据/窗口"。

**框架B — 实施交付类**

```
【当前阶段】
  <一句话描述项目当前阶段，如：实施调试>
【进展说明】
  今日进展：
  1）、<当日具体进展>
  2）、...
【待办计划】
  1）、<下一工作日计划>
  2）、...（无则填"无"）
【协调事项】
  1）、<阻塞点协调事项>
  2）、...（无则填"无"）
【风险提示】
  1）、<项目风险>
  2）、...（无则填"无"）
```

> 任一章节无内容时统一填"无"，保持模板结构完整。

**框架C — 会议类（四要素必填：主题 / 内容 / 结论建议 / 后续跟踪计划）**

```
【会议主题】
  <会议主题，一句话概括会议目的，如：XX项目周例会 / XX故障复盘会>
【会议内容】
  1）、<议题或讨论要点>
  2）、...（无则填"无"）
【结论与建议】
  1）、<形成的结论、决议或建议>
  2）、...（无则填"无"）
【后续跟踪计划】
  1）、<待跟踪事项 + 责任人 + 时间节点>
  2）、...（无则填"无"）
```

> 会议类强制四要素齐全：主题、内容、结论建议、后续跟踪计划。若用户未提供某要素，先尝试从上下文推断，推断不出则**显式追问**该要素，不在要素缺失情况下提交。

**框架D — 验收与报告编写类（必填：具体文档 + 计划完成时间/进度）**

```
【编写文档】
  <具体文档名称/清单，如：《XX项目验收报告》《XX数据库巡检总结》>
【内容/进度说明】
  1）、<文档涵盖的主要内容或当前编写进度>
  2）、...（无则填"无"）
【计划完成时间】
  <计划完成时间节点或里程碑，如：2026-09-30 完成初稿评审>
【当前状态】
  <进行中 / 已完成初稿 / 已评审 / 已提交客户>
【待办计划】
  1）、<下一步工作>
  2）、...（无则填"无"）
【协调事项】
  1）、<需协调客户/二线/产研的事项>
  2）、...（无则填"无"）
【风险提示】
  1）、<文档交付或验收风险>
  2）、...（无则填"无"）
```

> 验收与报告编写类强制两项齐全：**具体文档名称**（不是泛指"写报告"）与**计划完成时间/进度**。若用户只说"在写报告"未给文档名或时间，先追问这两项再提交。
> 验收场景下"当前状态"常填"已通过验收/验收中/待客户签字"；报告编写常填"初稿完成/评审中/已提交"。

| 章节 | 抽取来源 | 填充规则 |
|------|----------|----------|

| 客户反馈 | 客户评价、闭环确认、待客户配合事项 | 故障多为闭环确认；实施多为客户侧阻塞（IP未分配/资源未到位） |

| 会议主题（仅框架C） | "关于…的会/XX会议"等信号 | 一句话概括会议目的，必填 |

| 后续跟踪计划（仅框架C） | "会后跟进/待跟踪/责任人/截止" | 事项+责任人+时间，编号列表；必填 |
| 编写文档（仅框架D） | 文档名称、清单、"写了《…》" | 具体文档名，必填（不准只写"报告"） |
| 内容/进度说明（仅框架D） | 文档涵盖内容、编写进度 | 编号列表；无则"无" |
| 计划完成时间（仅框架D） | "计划X日前/预计X完成/里程碑" | 明确时间节点，必填 |
| 当前状态（仅框架D） | 进行中/初稿/评审/已提交/已验收 | 一句话状态 |

## 执行流程（MES 报工，主路径）

### Step 1: 接收用户工作内容

用户输入自然语言描述的工作内容，可含多天、多事项，示例：

```
今天处理了一个Oracle数据库hang起故障，排查发现归档写入慢，清理后恢复，
已给客户汇报；客户要求明天出报告，需要二线协助分析osw。
```

### Step 2: 信息抽取与结构化

自动识别并提取：

| 要素 | 提取内容 |
|------|----------|
| 工作日期 | 用户输入日期或默认今天 |
| 工作大类 | 五类之一（服务-故障分析 / 服务-主动计划 / 实施交付 / 会议 / 验收与报告编写） |
| 涉及数据库 / 项目 | 提取数据库名或项目名称 |
| 各章节要点 | 工作情况、客户反馈、待办、协调、风险 |
| 量化数据 | 提取数字指标（检查X套、耗时X分钟、优化X%） |
| 工时 | 用户输入或根据内容估算（需用户确认） |

### Step 3: 生成结构化报工备注（remark）

按识别到的大类，套用对应框架（A/B/C/D）组织 remark 文本，示例：

```
【工作情况】
1）、处置Oracle数据库hang起问题
2）、分析hang起原因（归档写入慢）
3）、清理后恢复正常
4）、向客户汇报
【客户反馈】
1）、故障已闭环
2）、需在指定日期前提交故障分析报告
【待办计划】
1）、进一步调查分析
2）、编制hang起故障分析报告
【协调事项】
1）、协调二线同事协助分析osw监控数据
【风险提示】
1）、调查分析原因较慢，存在客户满意度风险
```

### Step 4: 校验与预览

展示将执行的报工记录，供用户确认：

| 字段 | 值 |
|------|-----|
| 日期 | 2026-05-28 |
| 工时 | 8h |
| 工作大类 | 服务类-故障分析 |
| 报工备注 | 【工作情况】1）、...【客户反馈】...【待办计划】... |
| 关联项目 | 云南移动2026年数据库代维驻场 |

**硬规则自检（提交前阻断，必须全部通过方可进入 Step 5）**：

生成预览前，先对照以下硬规则自检。**校验粒度分两级**：「强制量化」为**报工级**（整条 remark 含 ≥1 个量化即过关，对应"所有报工必须包含至少1个量化数据"）；其余各项为**逐工作项级**（对【工作情况】每一条单独校验、逐项过关）。**任一不通过则绝不提交、回退让用户补充**，并在回复中明确列出「第几条 + 未通过项 + 需补充什么」，不展示"待确认提交"的预览：

| 自检项 | 校验粒度 | 通过条件 | 未通过处理 |
|--------|----------|----------|------------|
| 禁止模糊描述 | 逐工作项 | 每条工作项无"处理问题/配合工作"等模糊词，均为明确动作+对象 | 回退，要求改写该条为结构化明确描述 |
| 强制量化 | **报工级** | 整条 remark（全部工作项合计）含至少 1 个量化数据（X套/Xh/X%/X条/X GB…）；**不要求每条工作项都带量化** | 回退，要求整条补充至少 1 个量化数据 |
| 结果导向 | 含结果状态（已完成/已闭环/处理中/阶段完成） | 回退，要求补充结果状态 |
| 成果记录 | 含交付成果（报告/文档/配置/dblink/表格等） | 回退，要求补充成果 |
| 计划衔接 | 含待办/明日计划（或明确填"无"并说明合理） | 回退，要求补充后续计划 |
| 优化类成功指标 | 工作含"优化/提升/调优/性能改善"时，remark 须含"提升X%（或具体成效）"**且**"客户目标Y" | 回退，要求补充提升幅度与客户目标 |
| 内容充分性（按工作项逐条追问） | 对【工作情况】中**每一条**单独校验：① 检查/复查/审计类须列**具体检查项目或范围**（不能只写"检查完成/已整改"）；② 模糊数量（多个/若干/部分系统）须明确**具体数字**；③ 查询/检查/分析须带**明确结果**（查到什么/发现什么/是否达标）。任一条不达标即针对该条追问 | 逐条回退：列出**第几条**缺什么（具体检查项/系统数/结果），补齐前禁止提交 |

> 自检通过后展示上方预览表，待用户确认再执行 Step 5 提交。**自检未通过绝不执行 `mes statistics add`。**

### Step 5: 执行报工（最终动作）

用户确认后执行：

```bash
mes statistics add \
  --type 1 \
  --rid {实施计划ID} \
  --start "{date} 09:00:00" \
  --end "{date} 18:00:00" \
  --hours {hours} \
  --remark "{结构化备注}" \
  --acc-id {合同子项ID} \
  --company-id {公司ID}
```

> 提交前务必确认 MES CLI 已登录（`mes auth status`）。未登录先引导用户 `mes cli 登录`。

### Step 6: 结果反馈

报工成功后展示：

```
✅ 报工成功
📅 日期：2026-05-28
⏱️ 工时：8h
📝 备注：【工作情况】1）、...
🔗 报工ID：12345
```

## 批量报工流程

当用户一次性输入多天工作内容时：

1. **按日期拆分**：识别"周一"、"5月26日"、"今天"等日期表述
2. **按事项拆分**：识别"1."、"2."、"首先"、"然后"等事项分隔符
3. **逐日/逐项识别大类**：每一天、每一项独立判定工作大类并套用对应框架
4. **逐条确认**：展示所有报工记录，用户确认后批量提交
5. **汇总反馈**：展示批量报工结果汇总

## 缺参处理策略

| 缺失参数 | 处理策略 |
|----------|----------|
| 工作日期 | 默认使用今天，向用户说明 |
| 工时 | 根据工作内容估算，必须用户确认 |
| 工作大类 | 按 §五类工作识别 规则判定，判定失败则追问 |
| 涉及数据库/项目 | 追问用户 |
| 量化数据 | 尝试从内容提取，缺失则标注"待补充" |
| 合同子项 | 使用用户历史报工中最近使用的 acc-id |
| 实施计划 | 使用用户当前活跃的实施计划 |

## 量化数据提取规则

从用户输入中自动提取以下量化指标：

| 指标类型 | 提取规则 | 示例 |
|----------|----------|------|
| 数量 | 提取"X套"、"X个"、"X条"等 | "12套数据库" → 12 |
| 耗时 | 提取"X分钟"、"X小时"、"Xs"等 | "耗时45min" → 45分钟 |
| 百分比 | 提取"X%"、"降至X"等 | "优化92%" → 92% |
| 数据量 | 提取"X GB"、"X TB"等 | "23.7GB数据" → 23.7GB |
| 次数 | 提取"第X次"、"X次"等 | "第2次巡检" → 2 |
| 对比数据 | 提取"从X到Y"、"X→Y"等 | "从12s降至0.3s" |

## 合规校验规则

| 校验项 | 规则 | 处理方式 |
|--------|------|----------|
| 工时上限 | 单日不超过 10h | 超限需标注原因并提醒用户 |
| remark长度 | 最少 10 字 | 自动补充量化数据至达标 |
| 时间格式 | YYYY-MM-DD HH:mm:ss | 自动格式化 |
| 不能跨天 | start 和 end 必须同一天 | 自动拆分为多条报工 |
| 工作大类 | 必须匹配五类之一 | 自动分类或追问用户 |
| 硬规则自检 | 禁止模糊/强制量化/结果导向/成果记录/计划衔接 全部通过 | 任一不通过 → 回退用户补充，禁止提交 |
| 优化类成功指标 | 含"优化/提升/调优/性能改善"须含"提升X%"且"客户目标Y" | 回退，要求补充提升幅度与客户目标 |
| 内容充分性 | 对【工作情况】每一条单独校验：检查/复查须列具体检查项；模糊数量须明确具体数；查询/检查须带明确结果 | 逐条回退，补齐前禁止提交 |

## 注意事项

1. **先预览后提交**：所有报工必须先展示预览，用户确认后再提交（禁止未经确认直接写 MES）
2. **五类识别优先**：以"服务类（故障分析/主动计划）+ 实施交付类 + 会议类 + 验收与报告编写类"五类及框架A/B/C/D 为唯一分类体系，旧八类模板不再作为主结构
3. **强制量化**：所有报工应含至少 1 个量化数据（无法提取则标"待补充"并提示）
4. **结果导向**：应含结果状态（已闭环/处理中/阶段完成）
5. **结构完整**：任一章节无内容填"无"，保持模板结构
6. **批量逐条确认**：批量报工逐条展示，用户可逐条或全部确认
7. **Word 非默认**：除非用户明确要求，不要生成 .docx；MES 提交才是交付物
8. **禁止模糊描述**：将"处理问题""配合工作"等模糊表述转换为明确动作+对象的结构化备注（如"配合安联人寿客户开展核心ADOS数据库灾备切换演练"而非"配合工作"）
9. **成果记录**：必须记录交付成果（报告/文档/配置/记录等）；无明确成果则标"待补充"
10. **计划衔接**：建议包含明日/后续计划，保持工作连续性；无则标"无"
11. **自检阻断提交**：提交前必须做硬规则自检（禁止模糊/强制量化/结果导向/成果记录/计划衔接），任一未通过则回退用户补充内容，绝不跳过自检直接 `mes statistics add`
12. **优化类强制成功指标**：凡涉及"优化/提升/调优/性能改善"的工作，remark 必须写明提升幅度（如"响应时间从12s降至0.3s，提升97%"）及客户目标（如"客户目标≤1s"），缺一则回退补充
13. **内容充分性逐条追问**：对【工作情况】的**每一条**工作项单独做内容充分性校验——检查/复查/审计类必须列具体检查项目或范围（禁只写"检查完成/已整改"）；"多个/若干/部分系统"等模糊数量必须明确具体数字；查询/检查/分析必须带明确结果（查到什么/发现什么/是否达标）。**任一条不满足即针对该条单独追问，补齐前禁止提交**

## （可选）Word 留存 —— 仅用户明确要求时执行

当用户说"顺便生成 word / 输出报工文档留存"时，才在 MES 提交之外额外产出 `.docx`。文档内容即 Step 3 的 remark 结构化文本。

流程：

1. **识别类型**：按 §五类工作识别 判定大类与子场景
2. **抽取内容**：将用户自然语言映射到各章节要点
3. **创建文档**：调用 `tencent-local-office-edit` 的 `create_doc` 生成空白 `.docx`，拿到 `file_id`
4. **写入章节**：用 `doc_insert_markdown` 将「标题 + 各章节（编号列表）」作为一段 Markdown 一次写入
5. **保存与呈现**：`save_file` 保存为 `<大类>报工_<YYYY-MM-DD>.docx`，再用 `present_files` 呈现

> 此模块不影响主流程；即使用户要 Word，也应先完成 MES 提交（或经用户确认两者顺序）。
