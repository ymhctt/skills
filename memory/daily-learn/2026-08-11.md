# Oracle 高水位降低实战

> 来源：墨天轮 https://www.modb.pro/db/2053014030713970688

## 一、背景与原理

### 1.1 什么是高水位线

Oracle 段（Segment）以**高水位线（High Water Mark，HWM）**标记曾经使用过的最高块地址。全表扫描时，Oracle 需要扫描 HWM 以下的所有块，包含已被 DELETE 腾空的块，因此：

- **DELETE 不降低 HWM**：数据行被标记删除，但块仍属于该段，全表扫描代价不减
- **TRUNCATE 直接重置 HWM**：适用于清空全表，不可回滚
- **MOVE / SHRINK** 是在保留数据的前提下降低 HWM 的两种主要方式

### 1.2 适用版本与场景

| 项目 | 说明 |
|------|------|
| 适用版本 | Oracle 10g / 11g / 12c / 19c（核心操作均适用，差异详见各步骤说明） |
| 工作模式 | 普通表 / 分区表均适用；支持 Data Guard 环境（注意 nologging 限制） |
| 核心场景 | 表空间使用率过高，业务侧完成历史数据 DELETE 后，高水位线未下降，需手动收缩段以释放已删除空间 |
| 关键前提 | 业务已完成历史数据 DELETE；目标表空间具备足够空闲（至少 1 倍表大小） |
| 操作风险 | MOVE 期间表上存在排他锁；SHRINK 仅需 ROW MOVEMENT 模式，锁代价更低 |

## 二、两种核心方法对比

| 对比维度 | MOVE | SHRINK SPACE |
|----------|------|--------------|
| **机制** | 重建段，数据紧密重排 | 原地收缩，向低地址迁移行 |
| **锁级别** | 排他锁（全程），MOVE 期间不可 DML（11g）；12.2+ ONLINE 模式锁粒度大幅降低 | 仅 HWM 调整瞬间短暂排他锁（毫秒级），全程可 DML |
| **是否释放空间给系统** | ✅ 可配合 DEALLOCATE | ✅ 自动释放给表空间 |
| **是否需要 ROWID 稳定** | ❌ ROWID 改变，索引失效，必须 REBUILD | ✅ ROWID 不变（仅 ASSM 表空间支持） |
| **索引维护** | Move 后所有普通索引变 UNUSABLE，必须手动 REBUILD（12.2 ONLINE MOVE 自动维护） | CASCADE 子句自动维护索引，无需单独 REBUILD |
| **表空间要求** | 目标表空间需有 1 倍以上表大小的空闲空间 | 仅需少量额外空间（块级整理） |
| **表空间模式** | ASSM / MSSM 均支持 | 仅支持 ASSM；MSSM 报 ORA-10635 |
| **LOB 段** | 支持（需单独指定 LOB 列） | 需使用 `SHRINK SPACE ... LOB (col_name)` 单独处理 |
| **分区表** | 支持 MOVE PARTITION，灵活控制粒度 | 支持，但分区索引需额外处理 |
| **IOT 表** | 支持 | 不支持 |
| **Bitmap Index** | MOVE 后需重建 | 所在表不支持 SHRINK |
| **函数索引** | MOVE 后需重建 | SHRINK COMPACT 阶段可能受限，建议先删索引再重建 |
| **DG 环境** | Force Logging 下禁用 NOLOGGING；支持 ONLINE（12.2+） | 完全兼容（不涉及 nologging） |
| **碎片消除程度** | 彻底，数据完全重排 | 部分（行级整理，块内仍可能有碎片） |
| **停机要求** | 11g 需停机；12.2+ 可在线（ONLINE） | 无需停机，可在业务高峰分两阶段执行 |
| **执行速度** | 快（批量重排，可开高并行） | COMPACT 阶段较慢（逐块整理）；HWM 调整瞬间完成 |
| **适用场景** | 停机窗口内大批量碎片表的彻底清理 | 7×24 在线系统、不可停机的生产环境 |

## 📄 了解MySQL触发器：探索触发器如何影响MySQL内存分配.md

MySQL服务器的性能有时会令人困惑，如果您曾经想知道触发器在影响MySQL服务器内存分配中的作用，这篇文章就是为您準備的。MySQL触发器是数据库管理员和开发人员的强大工具，使他们能够自动化任务，强制执行数据一致性，并无缝响应数据库中的事件。

在这里，我们首先介绍MySQL触发器的基础知识，然后我们更深入地探索它们对内存使用的影响，并提供优化MySQL服务器性能的策略。

## MySQL中的触发器是什么？

MySQL中的触发器是一个在数据库管理中起着关键作用的数据库对象。它本质上是一组指令或程序，针对数据库中发生的特定事件或操作而自动执行。这些事件称为触发事件，可以包括在数据库表中插入、更新或删除记录等操作。

触发器的重要性在于它们能够强制执行数据完整性和自动化各种数据库相关任务。当触发事件发生时，关联的触发器将被执行，允许您执行验证数据、记录更改或保持引用完整性等操作。触发器作为保障措施，以确保满足或始终如一地执行某些条件或行动，从而[提高数据库的可靠性和一致性](https://www.percona.com/blog/triggers-and-updatable-views/)。

触发器执行是该机制的一个关键方面。当触发事件发生时，触发器的逻辑会自动调用，使其及时响应事件。这种实时响应能力确保数据保持准确，并符合预定义的规则或操作。

## 不同类型的MySQL触发器

MySQL支持各种类型的触发器，主要根据触发事件的执行时间进行分类。了解这些触发类型之间的差异对于在数据库管理中有效利用它们至关重要，因为它们服务于不同的目的，并在数据库操作的不同阶段执行。

### 行级触发器

MySQL中的行级触发器是一种响应表中单个行更改的触发器。这些触发器对每个受影响的行执行，使其成为基于特定数据修改自定义操作的强大工具。以下是行级触发器如何为每个受影响行工作的分步说明：

**触发激活**：当触发事件（如UPDATE语句）发生在具有关联行级触发的表上时，触发器将被激活。

**受影响的行**：如果触发事件影响多个行（例如，更新表格中的多行），则行级触发器将针对每个受影响的行单独执行。

**每行执行**：对于每个受影响的行，触发器的代码都会被执行。此代码可以包括触发器中定义的SQL语句、程序或其他操作。

**访问旧值和新值**：在触发代码中，您可以访问当前行每列的旧值和新值。OLD值表示修改前的数据，而NEW值表示修改后的数据。这允许您根据对每行所做的具体更改来比较和操作数据。

**条件逻辑**：行级触发器通常包括条件逻辑，该逻辑根据旧数据集和新数据集中的值来确定要采取的行动。此逻辑可用于强制执行数据完整性规则、生成审计日志或实现自定义业务逻辑。

**自定义操作**：触发器的操作是根据每行的具体要求自定义的。这种对单个行的精细控制允许对数据库中的更改进行定制响应。

**触发器完成**：一旦触发器的代码为一行执行，它就会进入下一个受影响的行（如果有的话）并重复该过程。这种情况一直持续到触发每个受影响的行。

**提交或回滚**：根据触发器和相关SQL语句的成功或失败，对行所做的更改可能会提交到数据库或回滚，以保持数据一致性。

### 语句级触发器

MySQL中的语句级触发器是响应触发它们的单个SQL语句而执行一次的数据库对象。这些触发器与受语句影响的单个行有关，而与整个语句有关。以下是对语句级触发器的解释，以及它们与行级触发器之间的关键区别：

#### 语句级触发器： 

**执行发生**：语句级触发器为每个触发SQL语句执行一次，无论受影响的行数如何。例如，如果UPDATE语句修改了100行，则与该语句相关的语句级触发器将仅对整个语句执行一次。

**数据访问**：与可以访问单个行的OLD和NEW值的行级触发器不同，语句级触发器通常不会访问特定的行数据。他们在更高的级别运作，更关心声明的整体影响。

**用例**：语句级触发器通常用于涉及整个语句的任务，例如维护摘要或汇总数据表、记录高级更改或应用语句级约束。
