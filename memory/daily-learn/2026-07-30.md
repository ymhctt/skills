## 📄 业务报死锁，为何MySQL的日志中没有记录.md

### 一、现象

某客户反馈，业务侧在执行update时报死锁，但是MySQL的错误日志和show engine innodb status均没有返回任何死锁信息。

![image-20250122111542636](/Users/yangminghan/Library/Application Support/typora-user-images/image-20250122111542636.png)

### 二、分析

先检查死锁相关参数，发现死锁检测和死锁信息输出都是打开的

![image-20250122133118329](/Users/yangminghan/Library/Application Support/typora-user-images/image-20250122133118329.png)

理论上所有的**innodb**死锁都会输出到错误日志，并且show engine innodb status 也会显示最近的一次死锁信息。例如：

![image-20250122133422811](/Users/yangminghan/Library/Application Support/typora-user-images/image-20250122133422811.png)

![image-20250122133518130](/Users/yangminghan/Library/Application Support/typora-user-images/image-20250122133518130.png)

但检查了客户环境，确实在业务报错的时间段并没有死锁的相关信息记录；问题在哪？

回到官方文档，打开innodb_print_all_deadlocks 和 show engine innodb status 记录的只是**innodb**的死锁信息。

![image-20250122133739011](/Users/yangminghan/Library/Application Support/typora-user-images/image-20250122133739011.png)

那除了innodb死锁，还有其他死锁吗？ 有的，metadata 死锁。看下面简单的例子

![image-20250122134534483](/Users/yangminghan/Library/Application Support/typora-user-images/image-20250122134534483.png)

出现了deadlock，查看innodb status 和 错误日志都没有输出相关信息

Innodb status 还是记录的老的死锁信息

![image-20250122134700626](/Users/yangminghan/Library/Application Support/typora-user-images/image-20250122134700626.png)

元数据死锁可能由并发ddl或并发的dml+ddl造成，由于死锁产生后的报错信息都是`ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction`，要注意同InnoDB deadlock的区分。

## 📄 MySQL_InnoDB表空间损坏恢复手册.md

# MySQL 8.0 InnoDB 表空间损坏恢复手册

> **适用场景**：MySQL 8.0（Oracle 官方版）因 undo 表空间损坏 + 业务表数据页损坏 + **数据字典 mysql.ibd 损坏**导致无法启动的完整恢复流程。
>
> **环境**：CentOS/RHEL 7、MySQL 8.0.19、InnoDB 引擎、独立表空间（innodb_file_per_table=ON）
>
> **覆盖三大场景**：
> 1. 🔴 **undo 表空间损坏** — 可 mv 走自动重建（中等难度）
> 2. 🟡 **业务表 .ibd 损坏** — 可 mv 走 + mysqldump 绕过（低难度）
> 3. 🔴🔴 **数据字典 mysql.ibd 损坏** — MySQL 8.0 单点故障，必须从备份恢复（极高难度）

---

## 一、故障现象

MySQL 启动失败，错误日志中出现以下关键报错：

```
# 阶段一：undo 表空间损坏
Space ID in fsp header is 131128, but in the page header it is 4294946832
FATAL: Tablespace id is 4294946832 in the data dictionary but in file ./undo_001 it is 4294967295!
Assertion failure: ut0ut.cc:536 thread ...

# 阶段二：业务表数据页损坏（移走 undo 文件后出现）
[ERROR] [InnoDB] Database page corruption on disk or a failed read of page
[page id: space=33639, page number=18837]. You may have to recover from a backup.

# 附加：业务表 .ibd 文件缺失
[Warning] Tablespace 127292, name './autocamel_ynd/lta_bf',
file './autocamel_ynd/lta_bf.ibd' is missing!
```

---

## 二、根因分析

### 2.1 undo 表空间损坏

- `undo_001` 文件头中的 space_id 为 `4294967295`（即 `0xFFFFFFFF`，未初始化的全 F 值）
- 数据字典记录的 space_id 为 `4294946832`，两者不匹配
- **文件头在校验阶段就触发 assertion，早于崩溃恢复的回滚阶段**

常见诱因：
- 磁盘空间写满
- `kill -9` 强杀 MySQL 进程
- 服务器异常掉电
- 底层磁盘/文件系统 I/O 异常
