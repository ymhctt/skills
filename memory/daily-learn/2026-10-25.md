## 📄 MogDB中max_dynamic_memory的大小.md

我们在使用和运维MogDB的时候可能会遇到内存不足导致的问题，报错信息通常为“memory is temporarily unavailable”或者“memory usage reach the max_dynamic_memory。”

其中max_process_memory是该实例能够使用的最大内存，属于POSTMASTER类型参数，重启才能生效。最佳实践要求该服务器上所有实例的max_process_memory之和不能超过物理内存的80%。

视图和报错中的max_dynamic_memory是指最大动态内存，我们可以通过dynamic_peak_memory值了解到动态内存使用的历史峰值。那么现在问题来了，max_dynamic_memory的值是由哪些参数来控制的呢？是否可以动态调整？

在src/common/backend/utils/mmgr/memprot.cpp文件中定义了max_dynamic_memory(maxChunksPerProcess)

```
maxChunksPerProcess = ((unsigned int)avail_mem >> BITS_IN_KB) - reserved_mem;
```

其中avail_mem的定义如下，既增加max_process_memory 或 减少 cstore_buffers 和 udf_memory_limit 的设置可以增加max_dynamic_memory。

```
int avail_mem = g_instance.attr.attr_memory.max_process_memory - g_instance.attr.attr_storage.cstore_buffers - udf_memory - (size >> BITS_IN_KB);
```

### 二、初步分析

很显然从上面的信息可以看出来，purge线程在获取最老的一个read view 用于清理undo和delete flag信息的时候，这个过程耗用了大量的CPU，这个过程是加trx_sys->mutex的，因为trx_sys->mvcc(MVCC) 是当前系统的read view的数据结构，其中包含2个链表结构：

- m_free：read view释放后会优先放到这个链表，可以重用(MVCC::get_view)
- m_views：当前使用中的read view**或者auto_commit并且不加锁的只读事务的read view close后放到里面（后面再讨论）**，对于最老的read view 应该放到其尾部。
  而pruge线程需要从m_views的尾部扫描，找到最老的read view，因此需要加trx_sys->mutex，而在分配read view 有些时候需要拿到trx_sys->mutex来维护MVCC的m_views和m_free。
  因此出现了堵塞，但是问题是为什么MVCC::get_oldest_view需要这么多的CPU呢？

随即我找了一下问题，发现有人已经遇到过了如下：

- [https://developer.aliyun.com/article/223320](https://links.jianshu.com/go?to=https%3A%2F%2Fdeveloper.aliyun.com%2Farticle%2F223320)
- [https://bugs.mysql.com/bug.php?id=88422](https://links.jianshu.com/go?to=https%3A%2F%2Fbugs.mysql.com%2Fbug.php%3Fid%3D88422)

貌似BUG状态并没有关闭，然后顺着文章进行一下分析，说不定可以有更多的见解。

### 三、read view的分配和select的类型

read view对于select 语句来讲非常的重要，其主要是用于判定数据的可见性，如果不可见还要联动undo，因此对于大查询比如select很久的语句，可能purge线程不能清理undo，导致undo巨大，并且数据不能清理掉，否则无法判定可见性。

### 今日新教训：fallback 链「僵尸模型」陷阱 ⚡⚡⚡

**场景**：三个微信推送 cron 全部 `status=error`。直觉会把它们归为同一故障，
但 `cron runs --id` 的 `errorReason` 分别为：

| cron | errorReason | 真实根因 |
|------|-------------|---------|
| 9fc7ca81 | `rate_limit` | 故障 M（M3/M2.7/M2.5 全 2056） |
| f730b7b4 | `model_not_found` | **故障 M**（M3/M2.5 是 2056，M2.1 是 2069 已下线） |
| a32216f6 | `rate_limit` | 故障 M（M3/M2.7/M2.5 全 2056） |

**关键洞察 1**：`errorReason` 只是**最后一个失败模型**的 reason。
fallback 链末级若指向一个「已下线但未从配置清理」的模型，
就会把整条错误的 reason 伪装成 `model_not_found` / `not_found_error`，
让人误以为「要换模型、要改配置、要爸爸介入」，而实际上**前两级都是配额问题，等就行**。

**关键洞察 2**：三个 cron 的 fallback 链**不一致**这件事本身是个隐患：
```
9fc7ca81 / a32216f6 : M3 → M2.7 → M2.5   (三级全活)
f730b7b4            : M3 → M2.5 → M2.1   (末级僵尸)
```
f730b7b4 天然少一次有效重试 → 在配额紧张的时段最先撞墙。

**可复用检查清单**（每次 cron 失败定级时）：
1. `cron runs --id <id> --limit 1` → 读**完整 error 文本**，不要只看 `errorReason`
2. 扫一遍 error 文本里**所有** `(reason)` 标记，统计各 reason 出现次数 → 出现次数最多的那个才是主因
3. 遇到 `model_not_found` / `not_found_error` → 先确认该模型是否已被下线
   （`grep '"id": "MiniMax' ~/.openclaw/openclaw.json` 对比 minimax 实际可用列表）
4. 只有**全部** fallback 都真失败且都不是 rate_limit 时，才考虑「需要爸爸/需要改配置」

### 关键洞察 3：静默期的「只读 + 不改配置」纪律

本次发现了一个**明确可修**的隐患（僵尸模型在配置里），
但修复动作是「编辑 `~/.openclaw/openclaw.json`」——属于核心配置改动。
按 AGENTS.md「先检查现有状态、保留/合并、别一了百了覆盖」+
「法定静默期 23:00-08:00」→ **本节点不执行、不推送**，
只把它记成待办，等白天窗口或爸爸确认。

> 这就是「有权限 ≠ 该行动」。记录 + 择时执行，比抢在静默期动手更安全。
