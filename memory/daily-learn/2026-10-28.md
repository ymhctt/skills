# daily-learn 2026-10-28

## 01:00 — 跨日首轮 heartbeat 的文件创建纪律

- **场景**：`cron:memory_refine` 在 00:00 跨日边界运行时，日志写进了 10-27 文件；01:00 再跑时今天（10-28）的 daily 文件尚不存在。
- **正确做法**：先 `ls memory/2026-10-28.md` 确认存在与否 → 不存在则用 `cat >` 新建（首行标题 + 指针段），再用 `cat >>` 追加本轮条目。
- **红线**：`write` 工具会**覆盖整个文件**（TOOLS.md 已固化），对已存在的 daily 文件追加内容必须用 `cat >>` 或 `edit`，否则丢历史。
- **新增教训**：跨日后的第一个整点（01:00）应该是「建文件 + 记录」的固定动作，且要在日志里留一行指针说明 00:00 那轮记录在哪，避免下个 session 以为 00:00 没跑过。

## 02:00 — cron ID 文档漂移的检测与修复

- **场景**：hourly memory_refine 想 `openclaw cron show <id>` 查 inbound媒体清理 cron → 返回 **`cron job not found`**。
- **关键判据**：**`not found` ≠ job 被删除**。SQLite `cron_jobs` 里 job 还在，只是 **id 变了**（job 重建/迁移后 id 重新生成），而 TOOLS.md / MEMORY.md 还写着旧 id。
- **正确排查顺序**：
  1. `openclaw cron list --all` → 看活着的 id（但可能因 id 变更而误判"消失"）
  2. `SELECT job_id,name,enabled FROM cron_jobs`（`mode=ro` 只读连接）→ **权威 id 清单**
  3. 对账：`grep -oE "[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}" TOOLS.md | sort -u` 与上一步逐一比对
- **本轮实锤**：live 8 个 job；文档里 `ce65d49c`(→07c53bc1)、`ea9ca7d6`(不存在)、`bcae370c`(→8a13c219)、`a32216f6`(历史故障记录，保留合理)
- **修复动作**：校正 id + 删除失效表格 + 合并重复表；**同时改 TOOLS.md 和 MEMORY.md**（AGENTS.md 规则九的三处同步）
- **教训**：文档漂移是**静默故障** —— 不报错、不影响运行，只在「照着文档执行」时才炸。
  → cron ID 至少每季度用 SQLite 对一次账；重建 job 后**立刻**改文档（AGENTS.md 规则九已固化，但这次是**迁移**导致 id 变，规则九没覆盖到）。

## 05:00 — provider 直连探测的复用（故障 M 无副作用预警）

- **场景**：hourly memory_refine 想确认 minimax 配额水位，但**绝不能**用 `openclaw message send` 自检（故障 T 铁律）。
- **正确做法**：直接 curl provider 的 anthropic-messages 端点，`max_tokens=8`：
  ```bash
  curl -s -o /tmp/pm_$m.json -w "%{http_code}\n" -X POST "https://api.minimaxi.com/anthropic/v1/messages" \
    -H "x-api-key: <apiKey>" -H "anthropic-version: 2023-06-01" \
    -H "content-type: application/json" \
    -d "{\"model\":\"$m\",\"max_tokens\":8,\"messages\":[{\"role\":\"user\",\"content\":\"hi\"}]}"
  ```
- **本轮实测**：M3 / M2.7 / M2.5 **全部 200** → 配额可用 → 无故障 M
- **价值**：零副作用、零 push 额度消耗，能在故障发生前**预警日内配额水位**（夜间 200 vs 白天 2056）
- **配套**：apiKey 从 `~/.openclaw/openclaw.json` → `models.providers.minimax.apiKey` 用 python 读出，**不要**在日志里回显明文

## 06:00 — Git porcelain ≠ 积压（3 个脏文件全是记忆追踪类）

- **场景**：memory_refine 做 Git 健康检查，`git status --porcelain | wc -l` 返回 **3**，乍看像积压。
- **判据**：必须看 `git status --porcelain` 的**具体条目**，不能只看计数：
  - `M memory/2026-10-28.md` / `M memory/daily-learn/2026-10-28.md` / `M memory/heartbeat-state.json`
  - → 三项全是**系统自己每轮写入的记忆追踪文件**，属正常写入，**不是积压**。
- **真正的积压判据**（照旧用 `@{u}`，规则：禁止用 origin/main）：
  ```bash
  git rev-parse --abbrev-ref --symbolic-full-name @{u}   # → workspace/openclaw-workspace
  git rev-list --left-right --count @{u}...HEAD          # (behind, ahead) → 0 0 = 无积压
  git status --porcelain                                # 看条目而非计数
  ```
- **教训**：脏文件计数是**信号**，条目才是**证据**。memory_refine 每轮都改记忆文件 → porcelain 天然 ≥1，不能当告警。
- **副作用**：本轮 `git rev-list` 与 `ls` 串联时被 `ls` 的非零退出码中断（`&&` 链断），Git 检查被跳过 → 之后改用 `;` 分隔独立执行，避免单点失败掩盖后续检查。
