# PostgreSQL REPACK 与逻辑复制槽位隔离：新参数 max_repack_replication_slots

> **来源**：公众号「digoal德哥」
> **链接**：https://mp.weixin.qq.com/s/xukMTOFtDAeuGO48mMgaVg
> **整理日期**：2026-04-18
> **适用版本**：PostgreSQL 19+

---

## 背景：凌晨被报警喊醒的痛点

**典型场景**：

```
ERROR: all replication slots are in use
```

`max_replication_slots = 10`，所有槽都被逻辑复制订阅占满，此时业务正在跑大表 `REPACK CONCURRENTLY`，REPACK 需要临时复制槽来保证一致性，现在抢不到槽直接报错。

**DBA 的两难**：

| 选项 | 代价 |
|------|------|
| 加大 `max_replication_slots` | 影响 WAL 保留开销，所有订阅需重新对接 |
| 禁止 REPACK | 业务不允许，表空间告急 |
| 半夜手动干预 | 非长久之计 |

---

## 核心解决方案：两个池子，各管各的

PostgreSQL 19 引入新参数 **`max_repack_replication_slots`**，将复制槽数组从逻辑上切成两段：

```
[0 ~ max_replication_slots)          → 逻辑复制订阅专用
[max_replication_slots ~ max_replication_slots + max_repack_replication_slots)  → REPACK 专用
```

**新旧对比**：

### 改动前（混用一个池子）

```
max_replication_slots = 10
┌─────────────────────────────────────┐
│ [槽1][槽2][槽3][槽4][槽5][槽6][槽7][槽8][槽9][槽10] │
└─────────────────────────────────────┘
   ↑逻辑复制订阅×8        ↑REPACK×2（用完了）

结果：REPACK 和订阅争抢剩下的 2 个槽，高并发时必报错
