## 📄 keepalived部署.md

## 一、安装

### 1	建议关闭防火墙并清空规则

```
iptables -F
systemctl stop firewalld
systemctl disable firewalld

#如打开防火墙，需开通规则
firewall-cmd --direct --permanent --add-rule ipv4 filter INPUT 0 --in-interface ens33 --destination 224.0.0.18 --protocol vrrp -j ACCEPT
firewall-cmd --reload
```



### 2	关闭selinux

```
setenforce 0
sed -i 's/SELINUX=enforcing/SELINUX=disabled/g' /etc/sysconfig/selinux
sed -i 's/SELINUX=enforcing/SELINUX=disabled/g' /etc/selinux/config
```



### 3 安装keepalived

**备注:主从需同时安装**

- yum安装`yum -y install keepalived`
- 编译安装

下载地址:
https://www.keepalived.org/download.html

安装步骤:

```
yum -y install openssl-devel
cd /usr/local/src
tar -zxvf keepalived-1.2.13.tar.gz
cd keepalived-1.2.13
./configure && make && make install
cp /usr/local/etc/rc.d/init.d/keepalived /etc/rc.d/init.d/
cp /usr/local/etc/sysconfig/keepalived /etc/sysconfig/
mkdir /etc/keepalived
cp /usr/local/etc/keepalived/keepalived.conf /etc/keepalived/
cp /usr/local/sbin/keepalived /usr/sbin/
chkconfig --add keepalived

# Redis真的变慢了吗？

首先，在开始之前，你需要弄清楚 Redis 是否真的变慢了？

如果你发现你的业务服务 API 响应延迟变长，首先你需要先排查服务内部，究竟是哪个环节拖慢了整个服务。

比较高效的做法是，在服务内部集成**链路追踪**，也就是在服务访问外部依赖的出入口，记录下每次请求外部依赖的响应延时。

![图片](Redis%E4%B8%BA%E4%BB%80%E4%B9%88%E5%8F%98%E6%85%A2%E4%BA%86%EF%BC%9F%E4%B8%80%E6%96%87%E8%AE%B2%E9%80%8F%E5%A6%82%E4%BD%95%E6%8E%92%E6%9F%A5Redis%E6%80%A7%E8%83%BD%E9%97%AE%E9%A2%98.assets/640-20220407100622954.jpeg)

如果你发现确实是操作 Redis 的这条链路耗时变长了，那么此刻你需要把焦点关注在业务服务到 Redis 这条链路上。

从你的业务服务到 Redis 这条链路变慢的原因可能也有 2 个：

1. 业务服务器到 Redis 服务器之间的网络存在问题，例如网络线路质量不佳，网络数据包在传输时存在延迟、丢包等情况
2. Redis 本身存在问题，需要进一步排查是什么原因导致 Redis 变慢

通常来说，第一种情况发生的概率比较小，如果是服务器之间网络存在问题，那部署在这台业务服务器上的所有服务都会发生网络延迟的情况，此时你需要联系网络运维同事，让其协助解决网络问题。

我们这篇文章，重点关注的是第二种情况。

也就是从 Redis 角度来排查，是否存在导致变慢的场景，以及都有哪些因素会导致 Redis 的延迟增加，然后针对性地进行优化。

排除网络原因，如何确认你的 Redis 是否真的变慢了？

首先，你需要对 Redis 进行基准性能测试，了解你的 Redis 在生产环境服务器上的基准性能。

## 📄 开源数据库风险.md

作为开源软件，存在以下风险

- 开源许可的复杂性

​		开源许可由于各种许可类型以及许可中的模糊语言而变得非常复杂。开源计划 (OSI) 列出了 58 种已批准的许可证类型，包括 GPL、LGPL、BSD、MIT 和 Mozilla 许可证。这些许可证中的每一个都带有一组不同的限制和义务——这些因素可能最终决定专有或“本土”软件应用程序是否需要根据开源许可协议发布。开源软件的企业用户必须信任他们的 IT 员工做出正确的技术和法律决策，这样组织才不会违反许可协议。在大多数情况下，企业开发人员完全不了解开源许可义务，并在未咨询其法律部门的情况下利用开源软件。即使公司的法律组织参与其中，每个开源合同的法律审查所涉及的成本也可能相当可观。这些许可协议通常用模棱两可的语言编写。

- 支持与维护

​		使用外部来源的软件时，可靠的技术支持是一项基本要求。在当今竞争异常激烈的商业环境中，可靠、多渠道（电话、电子邮件等）、24x7x365 全天候支持对于任务关键型应用程序来说是必不可少的。IT 组织越来越需要高水平的服务，在许多情况下，他们的应用程序受制于服务水平协议中确定的可用性、可靠性和性能阈值。如果没有可靠的技术支持，IT 组织将承担很大的风险，因为即使是简单的技术支持问题也可能导致重大项目延迟、开发人员时间损失、应用程序停机等。

开源数据库驱动解决方案没有组织的技术支持。充其量，这些项目提供了在线论坛，开发人员可以在其中提交问题、错误报告等。开发人员不保证会提供响应，并且没有任何保证或合同来规范解决方案的响应时间。开源数据库驱动项目团队根本缺乏提供可靠技术支持的资源。如果组织在驱动程序的安装或配置过程中遇到问题、在生产环境中部署驱动程序时出现的性能或可伸缩性问题、升级驱动程序时出现的问题，则组织必须依靠自己的开发资源来解决问题一个新版本，等等。

- 安全

微软旗下的全球最大的开源软件平台 GitHub 发现，17% 的软件漏洞是出于恶意目的而植入的。 

[GitHub 报告称，在昨天发布的 2020 Octoverse 报告](https://octoverse.github.com/#securing-software)中，恶意行为者故意将近五分之一的软件错误放入代码中。 

- 开源组件并非生而平等。有些从一开始就很脆弱，而另一些则随着时间的推移而变坏。
- 使用变得更加复杂。随着数百亿的下载量，管理库和直接依赖项变得越来越困难。
- 传递依赖：如果您使用的是 Maven (Java)、Bower (JavaScript)、Bundler (Ruby) 等依赖管理工具，那么您会自动引入第三方依赖——这是您无法承担的责任。

[Fortify](https://www.microfocus.com/solutions/application-security)首选的软件组合分析 (SCA) 合作伙伴 [Sonatype](https://www.sonatype.com/)的研究团队最近在其最新 [的软件供应链状态中](https://www.sonatype.com/press-release-blog/2019-state-of-the-software-supply-chain-report-reveals-best-practices-from-36000-open-source-software-development-teams) 发现：

平均每年有 300,000 多个开源组件被公司下载

2018 年，在数十亿次开源组件发布下载中，十分之一的开源组件存在已知安全漏洞 (10.3%)。

51% 的 JavaScript 包下载包含已知的安全漏洞。

自 2014 年以来，已确认或疑似与开源相关的违规行为增加了 71%

根据 WhiteSource 的数据，在 2015 年和 2016 年，安全漏洞的数量每年不超过 1,500 个，但在 2017 年和 2018 年，这一数字飙升至每年 4,000 多个。
