## 📄 【奇怪】MySQL DDL后执行计划乱了？.md



### 一、现象

用户反馈在对某表做ddl后，出现很多该表相关的慢查询。这些查询之前性能较好，怀疑执行计划受ddl影响，需定位更因。



### 二、分析

首先检查统计信息相关配置是否合理。该实例版本为mariadb 10.3.31，mariadb 10.0以后可以通过设置use_stat_tables参数，配置独立于存储引擎之外的统计信息采集和使用能力。相关统计信息存储在 mysql.table_stats, mysql.column_stats 和 mysql.index_stats表中。这个参数在10.4及以后的版本默认启用，use_stat_tables的参数及含义如下

| 值                          | 含义                                                         |
| :-------------------------- | :----------------------------------------------------------- |
| `never`                     | 优化器不使用统计表中的数据（MariaDB 10.4.0 及以下版本的默认设置）。 |
| `complementary`             | 如果存储引擎没有提供相同类型的数据，优化器将使用统计表中的数据。 |
| `preferably`                | 优先使用统计表中的数据，如果统计表中没有数据，则使用存储引擎中的数据。 |
| `complementary_for_queries` | 与 `complementary` 相同，但仅用于查询（以避免不必要地收集 `ANALYZE TABLE`）。从 MariaDB 10.4.1 开始可用。 |
| `preferably_for_queries`    | 与 `preferably` 相同，但仅用于查询（以避免不必要地收集 `ANALYZE TABLE`）。从 MariaDB 10.4.1 开始可用且为默认设置。 |

该实例use_stat_tables为默认值NEVER，即mariadb在执行SQL时，优化器不使用统计表中的数据，而使用存储引擎提供的统计信息。

接着检查innodb统计信息相关参数

innodb_stats_persistent=ON 说明表和索引的统计信息持久化存放在mysql.innodb_table_stats和mysql.innodb_index_stats表中。

innodb_stats_auto_recalc=ON 表示统计信息自动收集是开启的。

同客户确认，该ddl语句是将表中decimal(1,0) modify为decimal(2,0) ，这种修改字段类型的操作只能选择ALGORITHM=COPY的方式执行。我们知道重建表的ddl操作，需要创建一个临时表，完成数据拷贝后做表的替换，期间dml会阻塞。而临时表在完成数据拷贝前table->stat_initialized=false，也就是临时表的统计信息是不会采集的。 

怀疑是ddl操作和统计信息采集有时间差，在统计信息采集前执行计划会有问题。

```c++
## 📄 MySQL5.7增加半同步备库.md

## 一、背景

客户某业务使用的MySQL单实例运行，存在较大的安全风险，需要搭建主备架构满足高可用的要求。由于业务的特殊性，需要确保数据不丢失。考虑到当前版本为5.7，决定采用半同步方案。



## 二、步骤

1、安装备库

```
 rpm -ivh mysql-community-common-5.7.41-1.el7.x86_64.rpm
 rpm -ivh mysql-community-libs-5.7.41-1.el7.x86_64.rpm
 rpm -ivh mysql-community-libs-compat-5.7.41-1.el7.x86_64.rpm 
 rpm -ivh mysql-community-devel-5.7.41-1.el7.x86_64.rpm
 rpm -ivh mysql-community-client-5.7.41-1.el7.x86_64.rpm
 rpm -ivh mysql-community-server-5.7.41-1.el7.x86_64.rpm
 
```

```

## 📄 通过LVM扩容逻辑卷.md

本文介绍了如何通过LVM（Logical Volume Manager）扩容一个逻辑卷LV（Logical Volume），适用于Linux系统ECS实例。

## 前提条件

- 您已经创建了一个逻辑卷。具体操作，请参见[通过LVM创建逻辑卷](https://help.aliyun.com/document_detail/131141.htm#task-1797417)。
- 云盘已经在控制台完成扩容。具体操作，请参见[操作步骤](https://help.aliyun.com/document_detail/113316.htm#section-aqh-w5c-3gz)。本文示例为/dev/vdf扩容了40 GiB。
- 为防止操作失误导致数据丢失，建议您操作前使用快照一致性组备份数据。具体操作，请参见[创建快照一致性组](https://help.aliyun.com/document_detail/199625.htm#task-1997214)。

## 操作步骤

1. 远程连接ECS实例。

   关于连接方式的介绍，请参见[ 连接方式概述 ](https://help.aliyun.com/document_detail/71529.htm#concept-tmr-pgx-wdb)。

2. 使用以下命令查看ECS实例中物理卷PV（Physical Volume）信息。

   ```undefined
   pvs
   ```

   回显信息中的`PV`列的值表示物理卷名称。

3. 可选：

   使用以下命令扩容分区。

   如果物理卷不是直接从裸设备（例如/dev/vdf）创建而是分区设备（例如/dev/vdf1），则需要先扩容分区，才能扩容物理卷。物理卷名称末尾的数字即为分区编号，例如/dev/vdf1的分区编号为1。如果末尾没有数字，则为裸设备，请跳过此步骤。

   ```xml
   growpart <物理卷名称> <分区编号>
   ```

   以下示例为扩容物理卷分区（/dev/vdf1），您需要根据实际情况修改物理卷名称。

   ```bash
   growpart /dev/vdf 1
   ```

4. 使用以下命令扩容物理卷（PV）。

   ```xml
   pvresize <物理卷名称>
   ```

   以下示例为扩容物理卷（/dev/vdf），您需要根据实际情况修改物理卷名称。

   ```bash
   pvresize /dev/vdf
   ```
