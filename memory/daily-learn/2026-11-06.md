## 📄 postgresql出错could not create semaphores: No space left on device.md

在postgres中，当max_connect设置过大，启动的时候会报错:

FATAL:  could not create semaphores: No space left on device

创建semaphores时空间参数不够，查询官网，有这么一段解释：

HINT:  This error does *not* mean that you have run out of disk space.  It occurs when either the system limit for the maximum number of semaphore sets (SEMMNI), or the system wide maximum number of semaphores (SEMMNS), would be exceeded.  You need to raise the respective kernel parameter.  Alternatively, reduce PostgreSQL‘s consumption of semaphores by reducing its max_connections parameter.
The PostgreSQL documentation contains more information about configuring your system for PostgreSQL.
解决的方法是改小max_connect，当业务不允许的情况下，修改内核参数，max_connect相关的内核参数有：

 ![postgresql出错could not create semaphores: No space left on device](postgresql%E5%87%BA%E9%94%99could%20not%20create%20semaphores:%20No%20space%20left%20on%20device.assets/PkwwVsGDmjDG9swnOi7SkjVAsMQAarn73E9S3mmSmcBzFyyMhdOmuZoSrnmdNrdCZ2IkJhLurqrk_Ni_5ZtHeA.jpeg)

 下面介绍如何修改内核参数

```
# ipcs -ls
 
------ Semaphore Limits --------
max number of arrays = 1280
max semaphores per array = 50100
max semaphores system wide = 64128000
max ops per semop call = 50100
semaphore max value = 32767
 
 
# cat  /proc/sys/kernel/sem
SEMMSL   SEMMNS         SEMOPM  SEMMNI
50100   128256000       50100   2560
```

SEMMSL 每个信号量set中信号量最大个数

SEMMNS linux系统中信号量最大个数

SEMOPM semop系统调用允许的信号量最大个数设置，设置成和SEMMSL一样即可

SEMMNI  linux系统信号量set最大个数

 

所以SEMMNS=SEMMSL*SEMMNI

修改 vi /etc/sysctl.conf 的以下参数

kernel.sem = 50100 128256000 50100 2560

sysctl -p生效

重启数据库即可

## 📄 MySQL cpu使用高，如何找到对应的sql等信息.md

这是一个非常经典的性能排查场景。我们将这个过程分为两个步骤：**OS 层定位** 和 **MySQL 层分析**。

### 第一步：使用 `top` 定位高 CPU 的线程 ID

MySQL 在 Linux 下是单进程多线程架构。普通的 `top` 命令只能看到 `mysqld` 进程整体的 CPU 消耗。要找到具体是哪个线程（Thread）占用了 CPU，需要开启线程模式。

1.  **找到 MySQL 的进程 ID (PID)**
    ```bash
    pidof mysqld
    # 假设输出为 12345
    ```

2.  **查看该进程下的所有线程**
    使用 `-H` 选项开启线程模式，`-p` 指定进程 ID。
    ```bash
    top -H -p 12345
    ```

3.  **获取线程号 (LWP / OS_ID)**
    在 `top` 界面中，按 `P` 键（大写）按 CPU 使用率排序。
    *   观察 **PID** 列（在线程模式下，这一列代表 **LWP**, Light Weight Process ID，即操作系统层面的线程 ID）。
    *   记下 CPU 占用最高的那个 **PID**（例如：`12389`）。

---

### 第二步：在 MySQL 中根据线程号查询详细信息

拿到 OS 层的线程 ID (`12389`) 后，我们需要利用 MySQL 的 `performance_schema` 来进行映射。

> **前提条件**：MySQL 的 `performance_schema` 必须开启（默认通常是开启的）。

请登录 MySQL 执行以下 SQL 查询。

#### 1. 基础映射：找到 MySQL 内部 ID
首先，将 OS 线程 ID 映射为 MySQL 内部的 `THREAD_ID` 和 `PROCESSLIST_ID`。

```sql
SELECT 
    THREAD_ID,        -- MySQL内部线程ID (用于查询P_S表)
    PROCESSLIST_ID,   -- SHOW PROCESSLIST中的ID
    NAME,             -- 线程类型 (前台/后台)
    PROCESSLIST_USER, --以此用户身份运行
    PROCESSLIST_HOST, 
    PROCESSLIST_DB
FROM performance_schema.threads 
WHERE THREAD_OS_ID = 12389; -- 这里填入 top 命令看到的 PID
```

#### 2. 查询当前正在执行的 SQL 和 事务信息
拿到上一步查到的 `THREAD_ID`（假设为 `100`）后，查询当前正在执行的语句和事务状态。
