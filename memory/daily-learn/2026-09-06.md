## 📄 MogDB数据库完美适配Grafana及Prometheus.md

Grafana是一个跨平台、开源的度量分析和可视化工具，可以通过对接各种数据源并作可视化展示。

Prometheus是著名开源监控项目，其监控任务由具体的exporter实现，exporter到目标端抓取监控数据，然后保存在TSDB时序数据库中。Prometheus也支持PromQL查询语言进行自定义的查询组合。

openGauss/MogDB数据库可以通过opengauss_exporter完美适配Grafana及Prometheus。

下面在麒麟arm测试环境下演示部署过程，x86环境需要替换相关下载安装包。

### 1.Prometheus部署

#### 1.1. 安装包下载

软件下载地址：https://prometheus.io/download/
下载文件prometheus-2.31.1.linux-arm64.tar.gz

#### 1.2. 创建prometheus用户

```
# useradd prometheus # password prometheus 
```

#### 1.3. 创建prometheus相应目录并解压安装包

```
# mkdir /appdata/prometheus # mkdir /appdata/prometheus/etc # mkdir /appdata/prometheus/log # mkdir /appdata/prometheus/data # tar -zxvf prometheus-2.31.1.linux-arm64.tar.gz -C /appdata/prometheus # chown -R prometheus: /appdata/prometheus # chmod -R 755 /appdata/prometheus 
```

#### 1.4. 使用prometheus用户检查安装版本

```
$ /appdata/prometheus/prometheus-2.31.1.linux-arm64/prometheus --version 
```

#### 1.5. 使用prometheus用户编辑配置文件

```
$ vi /appdata/prometheus/etc/prometheus.yml 
```

内容如下

```
# my global config global:  scrape_interval:     15s # Set the scrape interval to every 15 seconds. Default is every 1 minute.  evaluation_interval: 15s # Evaluate rules every 15 seconds. The default is every 1 minute.  # scrape_timeout is set to the global default (10s). # Alertmanager configuration alerting:  alertmanagers:  - static_configs:    - targets: # Load rules once and periodically evaluate them according to the global 'evaluation_interval'. rule_files:  # - "first_rules.yml"  # - "second_rules.yml" # A scrape configuration containing exactly one endpoint to scrape: # Here it's Prometheus itself. scrape_configs:  - job_name: 'prometheus'    static_configs:    - targets: ['x.x.x.x:50090'] 
```

## 孤儿序列

创建序列可以使用serial，也可以自己建表时指定nextval，看个例子

```
postgres=# create table t1(id serial);
CREATE TABLE
postgres=# \d+ t1
                                                       Table "public.t1"
 Column |  Type   | Collation | Nullable |            Default             | Storage | Compression | Stats target | Description 
--------+---------+-----------+----------+--------------------------------+---------+-------------+--------------+-------------
 id     | integer |           | not null | nextval('t1_id_seq'::regclass) | plain   |             |              | 
Access method: heap

postgres=# create sequence myseq;
CREATE SEQUENCE
postgres=# create table t2(id int default nextval('myseq'));   ---建表时指定nextval
CREATE TABLE
postgres=# \d+ t2
                                                     Table "public.t2"
 Column |  Type   | Collation | Nullable |          Default           | Storage | Compression | Stats target | Description 
--------+---------+-----------+----------+----------------------------+---------+-------------+--------------+-------------
 id     | integer |           |          | nextval('myseq'::regclass) | plain   |             |              | 
Access method: heap
```

可以看到serial一步到位，数据库自动帮你建了序列并设置了默认值，同时还添加了not null的约束。

那让我们删除一下试试

```
postgres=# drop table t1;
DROP TABLE
postgres=# drop table t2;
DROP TABLE
postgres=# \d

 Schema | Name  |   Type   |  Owner   
--------+-------+----------+----------
 public | myseq | sequence | postgres
(1 row)
```

## 📄 开源数据库风险.md

作为开源软件，存在以下风险

- 开源许可的复杂性

​		开源许可由于各种许可类型以及许可中的模糊语言而变得非常复杂。开源计划 (OSI) 列出了 58 种已批准的许可证类型，包括 GPL、LGPL、BSD、MIT 和 Mozilla 许可证。这些许可证中的每一个都带有一组不同的限制和义务——这些因素可能最终决定专有或“本土”软件应用程序是否需要根据开源许可协议发布。开源软件的企业用户必须信任他们的 IT 员工做出正确的技术和法律决策，这样组织才不会违反许可协议。在大多数情况下，企业开发人员完全不了解开源许可义务，并在未咨询其法律部门的情况下利用开源软件。即使公司的法律组织参与其中，每个开源合同的法律审查所涉及的成本也可能相当可观。这些许可协议通常用模棱两可的语言编写。

- 支持与维护

​		使用外部来源的软件时，可靠的技术支持是一项基本要求。在当今竞争异常激烈的商业环境中，可靠、多渠道（电话、电子邮件等）、24x7x365 全天候支持对于任务关键型应用程序来说是必不可少的。IT 组织越来越需要高水平的服务，在许多情况下，他们的应用程序受制于服务水平协议中确定的可用性、可靠性和性能阈值。如果没有可靠的技术支持，IT 组织将承担很大的风险，因为即使是简单的技术支持问题也可能导致重大项目延迟、开发人员时间损失、应用程序停机等。

开源数据库驱动解决方案没有组织的技术支持。充其量，这些项目提供了在线论坛，开发人员可以在其中提交问题、错误报告等。开发人员不保证会提供响应，并且没有任何保证或合同来规范解决方案的响应时间。开源数据库驱动项目团队根本缺乏提供可靠技术支持的资源。如果组织在驱动程序的安装或配置过程中遇到问题、在生产环境中部署驱动程序时出现的性能或可伸缩性问题、升级驱动程序时出现的问题，则组织必须依靠自己的开发资源来解决问题一个新版本，等等。

- 安全

微软旗下的全球最大的开源软件平台 GitHub 发现，17% 的软件漏洞是出于恶意目的而植入的。 

[GitHub 报告称，在昨天发布的 2020 Octoverse 报告](https://octoverse.github.com/#securing-software)中，恶意行为者故意将近五分之一的软件错误放入代码中。 

- 开源组件并非生而平等。有些从一开始就很脆弱，而另一些则随着时间的推移而变坏。
- 使用变得更加复杂。随着数百亿的下载量，管理库和直接依赖项变得越来越困难。
- 传递依赖：如果您使用的是 Maven (Java)、Bower (JavaScript)、Bundler (Ruby) 等依赖管理工具，那么您会自动引入第三方依赖——这是您无法承担的责任。

[Fortify](https://www.microfocus.com/solutions/application-security)首选的软件组合分析 (SCA) 合作伙伴 [Sonatype](https://www.sonatype.com/)的研究团队最近在其最新 [的软件供应链状态中](https://www.sonatype.com/press-release-blog/2019-state-of-the-software-supply-chain-report-reveals-best-practices-from-36000-open-source-software-development-teams) 发现：

平均每年有 300,000 多个开源组件被公司下载

2018 年，在数十亿次开源组件发布下载中，十分之一的开源组件存在已知安全漏洞 (10.3%)。

51% 的 JavaScript 包下载包含已知的安全漏洞。

自 2014 年以来，已确认或疑似与开源相关的违规行为增加了 71%

根据 WhiteSource 的数据，在 2015 年和 2016 年，安全漏洞的数量每年不超过 1,500 个，但在 2017 年和 2018 年，这一数字飙升至每年 4,000 多个。
