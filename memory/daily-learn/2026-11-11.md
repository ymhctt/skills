## 📖 故事背景

90 年代初期，澳大利亚学术网络的出口带宽只有 **512Kbps**，仅为同期美国学术网络的 1/10。

在这种情况下，**Andrew Tridgell**（澳大利亚国立大学博士生）和 **Paul Mackerras** 面临一个问题：需要在澳大利亚和美国之间同步文件。如果用传统文件传输协议（如 FTP），**每次都需要传输完整文件**，512Kbps 的带宽完全不够用。

于是，rsync 算法在这种"带宽极度受限"的压力下被逼了出来。

## 🔄 算法演进流程图

```
┌─────────────────────────────────────────────────────────────────┐
│                      起点：跨澳美同步文件                          │
│                  （512Kbps 带宽，无法承受完整传输）                  │
└──────────────────────────────┬──────────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│                 【第1版】压缩 + 传输（Compression）                │
│                                                                  │
│   方案：先把文件压缩，再传输                                        │
│   ✅ 优点：文件变小，传输变快                                       │
│   ❌ 问题：文件只改 1 个字符，也要传整个压缩包，太浪费               │
└──────────────────────────────┬──────────────────────────────────┘
                               │  "还是太大"
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│            【第2版】保留原始副本 + 增量修改（Delta）                  │
│                                                                  │
│   方案：服务器保留原始文件，客户端只发送"第 N 个字符改成 X"           │
│   ✅ 优点：真正做到只传变化的部分                                   │
│   ❌ 问题：服务器需要保留原始文件 → 存储空间是大问题                 │
└──────────────────────────────┬──────────────────────────────────┘
                               │  "服务器存不起"
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│               【第3版】全量校验和对比（Full Checksum）               │
│                                                                  │
│   方案：客户端发文件校验和 → 服务器对比 → 只传不同的部分             │

## 一、主备数据不一致

### 1.1 定位根因

#### 1.1.1 从库写入数据

1、 这里分多种情况，常用的架构里因为前段应用访问的vip，因网络心跳问题，在主从节点上vip跳动，导致分别在两边都写入。通称脑裂现象。
![image.png](https://oss-emcsprod-public.modb.pro/image/editor/20220930-8eec4e87-f27d-4486-8eb7-2b1194bb58ce.png)
2、 双主情况下，为了保证负载，业务特性，双节点都在写，但因为复制进程断开或延迟存在，导致两个节点都写入同样的数据。复制破坏被迫停止，业务持续当中，这种情况破坏性越来越扩大。
![image.png](https://oss-emcsprod-public.modb.pro/image/editor/20220930-7d6cafe1-a76f-4248-9398-1842092cbbb1.png)
3、 从库人为做了操作：误链接从节点进行操作.
![image.png](https://oss-emcsprod-public.modb.pro/image/editor/20220930-2c43ff7e-a730-44fe-91ed-bfa3ca2ebc37.png)

#### 1.1.2.binlog非row格式

binlog三种模式，不管statement模式 还是mixed模式都有可能会用sql语句方式，把不应该操作的数据进行更改。最终数据不一致。
![image.png](https://oss-emcsprod-public.modb.pro/image/editor/20220930-e9cdbb3a-4c53-40d6-a4e1-6c4c7f77ac80.png)

#### 1.1.3.存储过程 或 触发器

存储过程或 触发器 因为本地调用的特有特性，有可能导致数据不一样结果。特别是时间和自增字段。

```
auto increment ，datetime ，timestamp
```

#### 1.1.4.sql_mode不一致

因为模式不同，对数据的处理不一样。典型的STRICT_TRANS_TABLES严谨模式，进行数据的严格校验，错误数据不能插入。当模式不一样下数据会被截断，最终就会存在不一致问题。
```

## 📄 MySQL Recover after DROP TABLE, innodb_file_per_table is OFF.md

Introduction

Human mistakes are inevitable. Wrong “DROP DATABASE” or “DROP TABLE” may destroy critical data on the MySQL server. Backups would help however they’re not always available. This situation is frightening but not hopeless. In many cases it is possible to recover almost all the data that was in the database or table.

Let’s look how we can do it. The recovery plan depends on whether InnoDB kept all data in a single ibdata1 or each table had its own tablespace . In this post we will consider the case innodb_file_per_table=OFF. This option assumes that all tables are stored in a common file, usually located at /var/lib/mysql/ibdata1.

 

Wrong action – table deletion
