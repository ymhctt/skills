# MySQL 数据库连接故障排查与优化报告

## 一、 故障概述

**故障现象：** 数据库服务出现拒绝新连接的异常，导致业务端/客户端无法正常建立数据库会话。 **核心报错：** 客户端尝试登录数据库时，抛出以下致命错误：

> ```
> ERROR 1135 (HY000): Can’t create a new thread (errno 11); if you are not out of available memory, you can consult the manual for a possible OS-dependent bug
> ```

## 二、 排查过程与原因分析

针对上述异常现象，技术团队对数据库运行状态及宿主机操作系统进行了基础排查，得出以下结论：

1. **资源监控排查：** 调取异常期间的系统监控指标，确认服务器物理内存（RAM）使用率处于正常范围，且系统未发生 Swap（交换空间）使用现象。这排除了因服务器 OOM（Out Of Memory，内存耗尽）导致无法分配新线程的可能性。
2. **系统限制排查：** 检查了操作系统的用户资源限制配置（`limits`）。结果显示，分配给数据库进程的各项资源限制均处于操作系统的默认初始值水平，未针对高并发数据库场景进行过调优。
3. **根本原因（Root Cause）：** 结合报错 `errno 11` (Resource temporarily unavailable) 与排查结果，确认此次故障的根本原因为**操作系统级的资源分配瓶颈**。突发的并发连接请求触发了操作系统对 `mysql` 用户所允许的最大线程数（`nproc`）限制，导致 MySQL 进程被操作系统拒绝创建新的工作线程，从而无法响应新的客户端连接请求。

## 三、 修复与优化建议

为彻底消除该资源瓶颈，保障数据库在持续高并发场景下的稳定运行，建议从操作系统层与数据库应用层双管齐下，执行以下调优操作：

### 1. 操作系统层优化 (System Limits)

修改操作系统的用户级资源限制配置文件（通常为 `/etc/security/limits.conf`），为 MySQL 运行用户大幅提升线程和文件描述符的上限：

```
# 增加最大线程/进程数限制，解决 errno 11 报错
mysql soft nproc 65535
mysql hard nproc 65535

# 同步增加最大文件描述符限制，预防高并发下的 Too many open files 报错
mysql soft nofile 65535
mysql hard nofile 65535
```

*(注：若 MySQL 通过 Systemd 管理，建议同步检查 `/usr/lib/systemd/system/mysqld.service` 中的 `LimitNOFILE` 与 `LimitNPROC` 或 `TasksMax` 参数是否也已放开。)*

### 2. 数据库层优化 (MySQL Configuration)

编辑 MySQL 全局配置文件（`my.cnf`），调整最大连接数及底层文件句柄限制，以匹配业务并发需求：

```
[mysqld]
# 提升数据库允许的最大并发连接数
max_connections = 4000

# 提升 MySQL 进程可打开的最大文件描述符数量
open_files_limit = 100000
```
