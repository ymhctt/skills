## 📄 Redis Cluster（集群）进行数据槽位（Slot）迁移.md


这是一组非常硬核的底层命令！你贴出的这四行代码，完整地描绘了 **Redis Cluster（集群）进行数据槽位（Slot）迁移的底层运转机制**。

在日常运维中，我们通常会使用 `redis-cli --cluster reshard` 这种高级工具来自动化完成扩缩容。但这些工具的底层，其实就是靠不断地循环执行你写的这几条原始命令来实现的。

理解了这些，你就真正摸透了 Redis 集群在迁移数据时，是如何做到“不停机、不丢数据”的。下面为你逐一详细拆解：

### 第一步：设置目标节点的状态（准备接客）

代码段

```
CLUSTER SETSLOT 300 IMPORTING <source-node-id>
```

- **在哪里执行**：目标节点（即将接收数据的机器）。
    
- **命令含义**：告诉目标节点：“请注意，你要开始从 `<source-node-id>` 这个源节点那里，接收第 `300` 号槽位（Slot）的数据了。”
    
- **底层作用**：目标节点收到这个指令后，会把该槽位标记为 `IMPORTING`（导入中）状态。此时，如果客户端带着 `ASKING` 标识来找它要 300 号槽位里的某个 Key，它就会破例受理，而不是像往常一样拒绝并重定向。
    

### 第二步：设置源节点的状态（准备送客）

代码段

```
CLUSTER SETSLOT 300 MIGRATING <target-node-id>
```

- **在哪里执行**：源节点（即将迁出数据的机器）。
    
- **命令含义**：告诉源节点：“你要开始把第 `300` 号槽位的数据，搬家到 `<target-node-id>` 去了。”
    
- **底层作用**：源节点把槽位标记为 `MIGRATING`（迁出中）状态。
    
- **⚠️ 核心精髓（ASK 重定向机制）**：一旦源节点进入这个状态，当客户端来找源节点读写 300 号槽位的某个 Key 时，会发生以下两种情况：
    
    1. 如果这个 Key **还没被搬走**（还在源节点本地）：源节点直接处理请求。
        
    2. 如果这个 Key **已经被搬走了**（或者根本不存在）：源节点会给客户端返回一个特殊的错误 `ASK <target-ip>:<port>`。客户端收到后，会立刻去连接目标节点，先发一条 `ASKING` 命令打招呼，然后再重新发送实际的读写操作。这就保证了迁移期间业务的连续性。
        

_(注意：必须先执行第一步，再执行第二步。如果反过来，源节点让客户端去目标节点找，而目标节点还没准备好接收，就会报错。)_

# Oracle 高水位降低实战

> 来源：墨天轮 https://www.modb.pro/db/2053014030713970688  
> 整理时间：2026-05-12

## 一、背景与原理

### 1.1 什么是高水位线

Oracle 段（Segment）以**高水位线（High Water Mark，HWM）**标记曾经使用过的最高块地址。全表扫描时，Oracle 需要扫描 HWM 以下的所有块，包含已被 DELETE 腾空的块，因此：

- **DELETE 不降低 HWM**：数据行被标记删除，但块仍属于该段，全表扫描代价不减
- **TRUNCATE 直接重置 HWM**：适用于清空全表，不可回滚
- **MOVE / SHRINK** 是在保留数据的前提下降低 HWM 的两种主要方式

### 1.2 适用版本与场景

| 项目 | 说明 |
|------|------|
| 适用版本 | Oracle 10g / 11g / 12c / 19c（核心操作均适用，差异详见各步骤说明） |
| 工作模式 | 普通表 / 分区表均适用；支持 Data Guard 环境（注意 nologging 限制） |
| 核心场景 | 表空间使用率过高，业务侧完成历史数据 DELETE 后，高水位线未下降，需手动收缩段以释放已删除空间 |
| 关键前提 | 业务已完成历史数据 DELETE；目标表空间具备足够空闲（至少 1 倍表大小） |
| 操作风险 | MOVE 期间表上存在排他锁；SHRINK 仅需 ROW MOVEMENT 模式，锁代价更低 |

## 二、两种核心方法对比

| 对比维度 | MOVE | SHRINK SPACE |
|----------|------|--------------|
| **机制** | 重建段，数据紧密重排 | 原地收缩，向低地址迁移行 |
| **锁级别** | 排他锁（全程），MOVE 期间不可 DML（11g）；12.2+ ONLINE 模式锁粒度大幅降低 | 仅 HWM 调整瞬间短暂排他锁（毫秒级），全程可 DML |
| **是否释放空间给系统** | ✅ 可配合 DEALLOCATE | ✅ 自动释放给表空间 |
| **是否需要 ROWID 稳定** | ❌ ROWID 改变，索引失效，必须 REBUILD | ✅ ROWID 不变（仅 ASSM 表空间支持） |
| **索引维护** | Move 后所有普通索引变 UNUSABLE，必须手动 REBUILD（12.2 ONLINE MOVE 自动维护） | CASCADE 子句自动维护索引，无需单独 REBUILD |
| **表空间要求** | 目标表空间需有 1 倍以上表大小的空闲空间 | 仅需少量额外空间（块级整理） |
| **表空间模式** | ASSM / MSSM 均支持 | 仅支持 ASSM；MSSM 报 ORA-10635 |
| **LOB 段** | 支持（需单独指定 LOB 列） | 需使用 `SHRINK SPACE ... LOB (col_name)` 单独处理 |
| **分区表** | 支持 MOVE PARTITION，灵活控制粒度 | 支持，但分区索引需额外处理 |
| **IOT 表** | 支持 | 不支持 |
| **Bitmap Index** | MOVE 后需重建 | 所在表不支持 SHRINK |
| **函数索引** | MOVE 后需重建 | SHRINK COMPACT 阶段可能受限，建议先删索引再重建 |
| **DG 环境** | Force Logging 下禁用 NOLOGGING；支持 ONLINE（12.2+） | 完全兼容（不涉及 nologging） |
| **碎片消除程度** | 彻底，数据完全重排 | 部分（行级整理，块内仍可能有碎片） |
| **停机要求** | 11g 需停机；12.2+ 可在线（ONLINE） | 无需停机，可在业务高峰分两阶段执行 |
| **执行速度** | 快（批量重排，可开高并行） | COMPACT 阶段较慢（逐块整理）；HWM 调整瞬间完成 |
| **适用场景** | 停机窗口内大批量碎片表的彻底清理 | 7×24 在线系统、不可停机的生产环境 |

## 📄 MogDB3.0兼容select子句非聚合列语法.md

在MySQL中如果不指定sql_mode 等于 ANSI或者ONLY_FULL_GROUP_BY时，select、having和order by 子句可以使用非聚合列。这种写法虽然不规范，也不能保证非聚合列返回数据的唯一性，但是在实际使用中还是比较常见的。

```
# SQL_mode不包含ANSI或者ONLY_FULL_GROUP_BY
mysql> select @@sql_mode;       
+--------------------------------------------+
| @@sql_mode                                 |
+--------------------------------------------+
| STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION |
+--------------------------------------------+
1 row in set (0.00 sec)

mysql> select * from t3;
+------+-------+------+
| id   | name  | age  |
+------+-------+------+
|    1 | andy  |   60 |
|    2 | lee   |   30 |
|    3 | yun   |   50 |
|    4 | tony  |   60 |
|    5 | candy |   30 |
|    6 | luss  |   50 |
+------+-------+------+
6 rows in set (0.00 sec)

mysql> select name,age from t3 group by age;
+------+------+
| name | age  |
+------+------+
| andy |   60 |
| lee  |   30 |
| yun  |   50 |
+------+------+
3 rows in set (0.00 sec)
```

这种在MySQL中“特殊”的语法，在PG、MogDB等数据库中执行会报错。导致迁移到其他数据库时业务侧需要做针对性的调整，增加了迁移的工作量。
