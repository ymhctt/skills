## 📄 redis acl 命令使用.md

# redis acl 命令

在Redis6.0之前的版本中，登陆Redis Server只需要输入密码（前提配置了密码 requirepass ）即 可，不需要输入用户名，而且密码也是明文配置到配置文件中，安全性不高。并且应用连接也使用该    
密码，导致应用有所有权限处理数据，风险也极高。在Redis6.0有了ACL之后，终于解决了这些不安 全的因素，可以按照不同的需求设置相关的用户和权限。本文来介绍下Redis 6.0 ACL相关的配置和 使用。

# 说明

```
Redis ACL 是向后兼容的，即默认情况下用户为default，使用的是requirepass配置的密码。要是不使用 
ACL功能，对旧版客户端来说完全一样。Redis Auth可以有2种方式进行工作：  
1:旧版本的使用方式，默认用户。兼容旧版本Redis的支持  
AUTH <password>  
2:新方式，还需要验证用户名  
AUTH <username> <password>  
因为需要验证用户名了，所以客户端的认证方式也多了参数： 

  ‐‐user <username>  验证用户名  
  ‐‐pass <password>  验证密码,是参数‐a的别名;配合‐‐user使用  
  ‐‐askpass          强制用户输入带有STDIN掩码的密码  

```

# 命令详解

```
> ACL help  
 1) ACL <subcommand> arg arg ... arg. Subcommands are:  
 2) LOAD                             ‐‐ 从ACL文件中重新载入用户信息.  
 3) SAVE                             ‐‐ 保存当前的用户配置信息到ACL文件.   4) LIST                             ‐‐ 以配置文件格式显示用户详细信息.  
 4) USERS                            ‐‐ 列出所有注册的用户名.  
 5) SETUSER <username> [attribs ...] ‐‐ 创建或则修改一个用户.  
 6) GETUSER <username>               ‐‐ 得到一个用户的详细信息.  
 7) DELUSER <username> [...]         ‐‐ 删除列表中的用户.  
 8) CAT                              ‐‐ 列出可用的类别.  
9) CAT <category>                   ‐‐ 列出指定类别中的命令.  
10) GENPASS [<bits>]                 ‐‐ 生成一个安全的用户密码.  
11) WHOAMI                           ‐‐ 返回当前的连接用户.  
12) LOG [<count> | RESET]            ‐‐ 显示ACL日志条目.  

```

## 📄 MySQL查询优化 (old).md

## 一、前言

提到MySQL查询优化，通常我们会想到那些看起来很复杂，涉及很多张表，返回数据特别多的SQL。但是有的查询只返回很少的数据执行时间也会特别长。为什么会出现这样的现象，这些SQL该如何优化？还有的时候业务代码明明没有更新，业务执行同样的SQL响应时间比之前突然增加了不少，数据库服务器负载一直居高不下，show processlist 发现有很多不同的SQL正在执行。我们应该怎样定位问题的原因，从哪里下手优化？

要解决这些问题，写出足够优化的SQL，我们首先要了解一条SQL语句是怎么执行的。下图是MySQL的架构示意图，MySQL分为两大部分Server层和存储引擎层。当客户端通过连接器与数据库建立连接后就可以执行SQL了，MySQL会对SQL的文本信息做语法和词法解析，然后优化器会选择一个开销最小的执行计划，最后由执行器通过接口去相应的存储引擎获取数据。



<img src="MySQL查询优化.assets/image-20210219170206020.png" alt="image-20210219170206020" style="zoom:50%;" />

要解决查询优化的问题，首先我们需要知道如何发现和定位慢查询，了解数据是如何存储以及MySQL是怎样访问数据的。清楚MySQL优化器的工作原理，学会分析SQL的执行计划。接下来我们将对这些问题一一讲解。由于目前绝大多数MySQL项目都使用Innodb引擎，本文内容只涉及Innodb引擎；



## 二、怎么发现慢SQL

获取慢SQL常用的有三种方式，可以通过processlist查看当前正在执行的SQL，从中发现问题SQL；也可以从慢查询日志和sys中相关视图中发现执行过的问题SQL；当然还可以通过抓包分析、死锁检测、业务日志等方式获取问题SQL，由于不常用本文就不展开分析了；

### 2.1 从当前查询中获取问题SQL

MySQL中可以使用select * from information_schema.processlist和show [full] processlist命令查看MySQL服务器内部当前线程正在执行的操作。两种方式返回的数据是相同的，show processlist只显示info字段前100个字符。注意，如果用户没有process权限则只能查看本用户发起的发起的连接线程信息。

- ID：连接标识。等于performance_schema.threads表的PROCESSLIST_ID字段，与CONNECTION_ID()函数返回值相同；如果需要kill一个查询需要用到它；
- USER：执行该操作的用户；
- HOST：发出该语句的客户端主机名或者IP：PORT；
- DB：该线程连接的数据库；
- Command：该连接当前执行的命令或状态；包括 sleep（休眠），query（查询）等等https://dev.mysql.com/doc/refman/8.0/en/thread-commands.html
- Time：线程处于当前状态的时间，单位是秒；
- State：当前线程正在执行的动作、事件和状态；一个SQL可能包含多个状态，大多数状态都是非常快速的，如果持续数秒则需要重点关注；这是分析问题最重要的一项指标；https://dev.mysql.com/doc/refman/8.0/en/general-thread-states.html
- Info：线程正在执行的语句或Null；

如果出现连接数大量增加，较多查询超时或者数据库cpu或IO等使用率增加时，可以通过processlist我查看目前有哪些SQL正在执行，执行的时间，是否在等待某些锁资源或者正在传输数据等等。

通常在查询processlist表的时候，我们可以将Command=’sleep‘和'Daemon'这类连接排除掉并按Time逆序输出，方便查看到执行时间较长的活跃连接。

```

mysql> select * from information_schema.processlist\G
*************************** 1. row ***************************
     ID: 5
   USER: event_scheduler
   HOST: localhost
     DB: NULL
COMMAND: Daemon
   TIME: 440535
  STATE: Waiting on empty queue
   INFO: NULL
*************************** 2. row ***************************
     ID: 22
   USER: test

## 📄 华为云企业级Redis评测第二期：大Key操作的影响.md

在前一篇文章[《华为云企业级Redis评测第一期：稳定性与扩容表现》](https://www.modb.pro/db/171623) 中，我们使用多线程压测工具memtier_benchmark对华为GaussDB(for Redis)和原生Redis进行了对比压测，发现原生Redis存在OOM和数据丢失的情况。反观华为GaussDB(for Redis)不仅性能稳定，还具备在压测过程中秒级扩容的能力，扩容操作对业务读写无影响。华为GaussDB(for Redis)支持全量数据落盘，GaussDB基础组件服务提供底层数据三副本冗余保存，能够保证数据零丢失。如果使用场景既要满足KV查询的高性能，又希望数据得到重视能够不丢，建议从原生Redis迁移到GaussDB(for Redis) 。

我们大多在实际生产环境中都遇到过big key对Redis性能的严重影响。接下来我们通过几个简单的实验，测试下对于大key这一“性能杀手”，GaussDB(for Redis)的表现怎样，和原生Redis相比在性能上有哪些改进。

#### 1、访问大key

首先分别在GaussDB(for Redis)和原生redis中创建一个大的hash类型的key。

编辑一个简单的lua脚本，向一个hash key中插入一千万条数据。

```
# vim redis-bigkey.lua
local result
for var=1,10000000,1 do
redis.call('hset',KEYS[1],var,var)
redis.call('lpush',KEYS[2],var)
redis.call('sadd',KEYS[3],var)
end
return result
```

向GaussDB(for Redis)【192.168.0.226:8635】中插入大key

```

### 📌 Git 告警误判第三次复发 —— 根因是「双错叠加」而非单一错 ref
三次误判的完整解剖：
| 时间 | 用的 ref | 数字 | 结论 | 真因 |
|---|---|---|---|---|
| 10-27 11:00 | `origin/main` | 0/0 | "瞬时快照已收敛" | 结论偶然对，但 ref 错 |
| 10-27 15:00 | `origin/main` | 18/40 | "真积压" | ❌ ref 错 → 完全虚假 |
| 10-27 07:20 | 早间汇总自带 | 17 ahead / 143 untracked | "有积压" | ❌ ref 错 + 瞬时快照 |
| 10-28 00:00 | `@{u}` | 0/0 | "Git 健康" | ✅ 正确 |

**教训固化**：`@{u}` 是唯一正确判据。且早间汇总的 Git 结论**必须二次复验**才可采信——
它跑在 07:20，此时 git_sync（07:00）刚 push 完，worktree 状态易被并发写入污染，
加上汇总脚本历史上用了 `origin/main` → 两个误差源叠加，放大了假积压数字。

### 📌 故障 K 的唯一解除路径确认（day-48）
穷举了所有自助可能：
- `mes auth login --help` → 三种方式：`--web`（浏览器 OAuth）/ `--device`（设备码）/ `--with-token`
- 三种**全部需要真实凭证**（浏览器登录 / 人工输入 token / 已知 token）
- `/root/.mes/config.yaml` → `token: ""`（空串，被清空）
- `/root/.mes/state.json` → 仅 `lastPageByKey`（业务缓存，**不含任何凭据**）
- 环境变量 → 无 MES 相关

→ **结论：故障 K 无自助路径，必须爸爸执行 `mes auth login`。**
这条以后不用再重复排查，直接问爸爸要登录即可。
