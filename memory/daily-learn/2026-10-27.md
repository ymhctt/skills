### 1. 故障判定必须走「唯一权威实测」，禁止跨轮次沿用故障标签
本轮 a32216f6 连续 4 天 error（10/23-10/26），若沿用上轮标签很容易直接写成「故障 K 持续」。
实际读 `cron_run_logs.error` → `FallbackSummaryError: All models failed (3)` + 三模型全 `rate_limit_error 2056`
+ `errorReason=rate_limit`（非 model_not_found）→ **故障 M**，与故障 K（MES 鉴权失败）根因和修复路径完全相反。

**判定顺序（复用）**：
1. `errorReason=rate_limit` → 故障 M（等 Token Plan 配额，不需爸爸）
2. error 文本含 `mes auth` / `mes_summary_t23.json` → 故障 K（需爸爸 `mes auth login`）
3. 都不含 → 工具调用链异常（故障 Q/S）

### 2. 双重阻断叠加的识别方法
本轮 a32216f6 存在**两个独立故障同时生效**：
- 故障 M（模型层 rate_limit）→ 09:40 cron 直接被拒，连 fetch 都没跑到
- 故障 K（MES token 失效）→ 即使 rate_limit 窗口过去，fetch 阶段仍拿不到数据

→ 结论：**修好任一个都不足以恢复 a32216f6**，必须双条件同时满足。
这解释了为什么「等 Token Plan 重置」这类单点修复方案在本例中注定无效。

### 3. burst 窗口假说的验证方法（可复用）
直接向 provider 发一条 `max_tokens=8` 的最小请求，看 HTTP 状态码：
- 全 200 → 配额在非高峰时段可用 → 不是硬性封顶，是时段性 burst
- 405/404 → 模型下线
- 429/2056 → 真·配额封顶

本轮 00:00 实测 M3/M2.7/M2.5 全 200，为「上午 cascade 撞窗」假说提供第 14 次复验支持。

### 4. 变种 V 修复的「两层」结构（重要，易漏）
清理已下线模型需要改**两个地方**：
- `~/.openclaw/openclaw.json` → `models.providers.<prov>.models[]`
- SQLite `cron_jobs.payload_fallbacks_json` → 每个 cron job 自己的 fallback 链

只改前者 = 僵尸模型在 fallback 链里复活 → 末级 `model_not_found` 覆盖 `errorReason` → 把真正的 `rate_limit` 误判成「模型配置坏了」。
本轮确认两层都干净（第 12 次）。

## 03:00 heartbeat 学习点

### 5. 故障 M 的性质再修正：从「月度耗尽」修正为「日内峰值瓶颈」（重要，影响所有后续决策）
TOOLS.md 历史记载曾把故障 M 定性为「月内配额耗尽，需等下个计费周期（10/1）重置」，
但 10/26-10/27 的实测数据推翻了这一假设：

| 时间 | provider 直连实测（max_tokens=8） | 结果 |
|---|---|---|
| 10/26 09:40 | a32216f6 cron 实际调用 | 三模型全 2056 Token Plan 上限 ❌ |
| 10/26 07:20 / 08:02 | 9fc7ca81 / f730b7b4 cron | 成功 + delivered=1 ✅ |
| 10/27 00:00 | provider 直连 curl | 全 200 ✅ |
| 10/27 03:00 | provider 直连 curl | 全 200 ✅（M3 / M2.7 / M2.5 三个都正常） |

→ **配额存在日内水位波动**：夜间回落到可用区间，白天上午 cascade 阶段被吃满。
→ **推论修正**：故障 M **不需要等月重置**，也**不需要充值**；它是一个**日内时段性问题**，
  且 09:40 a32216f6 因同时承担 fetch + 长任务消耗，最容易在白天高峰撞墙。
→ **决策含义**：故障 M 一律**静默等待自然恢复**，绝不手动补发、绝不 enable/disable 折腾、
  更不能把它归到「要爸爸处理」的类别里（那会误耗爸爸注意力）。

### 6. 心跳自检可以做的「无副作用」诊断升级
除了 `cron runs` / `cron list --all` / SQLite `mode=ro` 查询，
**provider 直连 curl 探测**（`max_tokens=8`）是一个被低估的只读诊断手段：
- 它能在**故障发生前**预警配额水位（夜间 200 vs 白天 2056）
- 它**完全不消耗 push 额度**、不触碰微信通道、不影响 cron 状态
- 它与「故障 T 铁律」完全兼容 —— 因为它根本不涉及 send
→ 已固化进心跳标准动作：**每次心跳对 M3/M2.7/M2.5 各发一次 8-token 探测**，成本约 3 次 curl。

### 7. provider 探测的判据表（复用）
| HTTP / 错误 | 含义 |
|---|---|
| 200 | 配额可用 ✅（该模型没下线也没撞窗） |
| 404 / `not_found_error 2069` | 模型已下线 → 需清理 provider models[] **和** cron fallback 链 |
| 429 / `rate_limit_error 2056` | Token Plan 撞顶 → 故障 M，等恢复，**不需爸爸** |
| 401 / 鉴权错 | provider apiKey 失效 → **需爸爸**（与故障 K 同级） |
