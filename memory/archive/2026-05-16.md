## 📄 MySQL不写binlog的N种场景.md

# MySQL 不写 Binlog 的 N 种场景

## 一、概述

Binlog（Binary Log）是 MySQL 记录数据变更的核心日志，但以下场景**不会记录 Binlog**。

---

## 二、不写 Binlog 的场景

### 1. `log_slave_updates = OFF`（从库设置）

**场景：** 主从复制架构中，如果从库实例设置了 `log_slave_updates=OFF`，则从库接收到的**主库变更**（relay log）不会被记录到从库的 binlog。

```sql
-- 查看当前配置
show variables like 'log_slave_updates';
```

**影响：**
- 该从库本地不会生成 binlog，无法再作为其他从库的主库
- 常用于**级联从库**的中间节点，避免日志无限传递

---

### 2. `log_bin` 未开启

**场景：** MySQL 实例未开启 binlog 功能。

```sql
-- 检查 binlog 是否开启
show variables like 'log_bin';
show master status;
```

**不写 binlog 的情况：**
- MySQL 编译时未带 `-DWITH_LOG_BIN`
- 配置文件 `my.cnf` 中未设置 `log-bin`
- **5.7 及以后**，GTID 复制模式要求必须开启 binlog

---

### 3. 临时表（Temp Table）操作

**场景：** 使用 `CREATE TEMPORARY TABLE` 创建的临时表，变更**不记录 binlog**。

```sql
CREATE TEMPORARY TABLE temp_data (id INT, name VARCHAR(100));
INSERT INTO temp_data VALUES (1, 'test');
```

## 📄 mysql.gtid_executed表gtid_executed变量gtid_purged变量的更改时机.md

via:https://www.jianshu.com/p/905d7e89a305

本节将集中讨论下面三种Gtid更新的时机，这部分相当重要，后面的故障案列会和这节有关。下面先来看一下他们的定义

- mysql.gtid_executed表：Gtid持久化的介质，Mysql启动阶段会读取这个表来获取gtid_executed变量的值。
- gtid_executed变量(show global variables)：Mysql数据库已经执行了哪些Gtid事务，处于内存中。show slave status中的Executed_Gtid_Set也取自这里。
- gtid_purged变量(show global variables)：由于binlog文件的删除(如purge binary logfiles或者超过expire_logs_days设置)已经丢失的Gtid事务，同时在搭建备库的我们使用set global gtid_purged变量来提示Mysql哪些Gtid事务我已经执行过了。

这也是我们DBA通常能够观察到的几种Gtid，有了前文的描述我们知道其中mysql.gtid_executed表是一种Gtid持久化的介质，而gtid_executed变量和gtid_purged变量则对应
了Gtid_state中的executed_gtids和lost_gtids内存数据。他们分别表示Mysql数据库执行了哪些Gtid事务，有哪些Gtid事务由于binlog文件的删除已经丢失了。
其次我们先来达成一个共识**gtid_executed变量一定是实时更新的不管主库和从库**。我们的讨论分为主库，从库和通用从源码的角度进行详细讨论。并且**约定都是打开Gtid**的情况下。最后给出最终总结。
