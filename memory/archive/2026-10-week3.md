### 1️⃣ 故障 K 连续两次「误判自愈」后确立权威判定法 ⚡⚡⚡⚡⚡

**背景**：故障 K = MES token 失效（`mes auth status` → Not logged in），9/11 起持续阻断 a32216f6 报工统计的数据链路。

**两次误判（本周最大教训）**：

| 误判 | 时间 | 当时依据 | 为什么错 |
|------|------|---------|---------|
| 误判 1 | 10/19 | cron run `input_tokens=105467`（数据量正常） | **token 量只说明模型请求已发出，不能证明 MES 鉴权通过** |
| 误判 2 | 10/20 | 09:40 `Exec failed: python3 analyze.py` → 判为「独立故障 Q 工具级故障」 | **这是故障 K 的下游症状**：未登录 → fetch 拿不到数据 → `/tmp/mes_summary_t23.json` 不存在 → analyze.py 无输入即失败 |

**纠正（10/21 00:00 固化进 TOOLS.md）**：
- ✅ **唯一权威判据** = `mes auth status` 返回值
  - `Not logged in (no token saved)` = 故障 K 未修复
  - 佐证 = `ls /tmp/mes_summary_t23.json`（不存在 = fetch 阶段必失败）
- ❌ **禁止**用 `input_tokens` / `durationMs` / cron status / 异常文本推断故障 K 状态
- ✅ **`Exec failed: analyze.py` 类「下游脚本无输入失败」应记为故障 K，不单独计故障 Q**（合并计数）
- ✅ **推广规则**：error 文本出现 `mes auth` / `mes_summary_t23.json` 字样 → 一律归故障 K

**本周实测轨迹（day-38 → day-45，均为权威实测）**：
```
10/19 09:41  OutboundDeliveryError ret=-2            → 故障 L（cron announce 路径被阻断）
10/20 09:41  Exec failed: python3 analyze.py          → 故障 K 下游（曾误判为故障 Q）
10/21 09:41  Exec failed: run mes auth → ...          → 故障 K 下游 + 故障 L 复合
10/22 09:40  rate_limit 2056 三模型全 fail             → 故障 M（卡在模型层，未走到 fetch）
10/26 02:00  mes auth status → Not logged in          → 故障 K 持续 day-45+ 权威确认
```

**关键认知（本周新增）**：**故障 K 与故障 M 可同时存在且互相遮蔽** ——
10/22-10/25 的 cron error 全是 rate_limit（卡在模型层，**还没走到 fetch**），
所以故障 K 在 error 文本里**完全看不见**，但底层数据链路依然是断的。
→ **必须两个都独立复测，不能只看 cron error 文本。**

**修复路径**：需爸爸执行 `mes auth login`（或联系 MES 管理员提权）。这是故障 K 的**唯一**解除方式，等不来自愈。

### 2️⃣ 「禁止用预判代替实测」被实测打脸 6 次 ⚡⚡⚡⚡⚡

**事件**：10/22 02:00-08:03 连续 6 次 heartbeat 预判「09:40 a32216f6 预计 fail = 故障 K 主动拒绝推送」。

**10:00 权威实测打脸**：
```

  minimax/MiniMax-M3:   rate_limit_error 2056 已达到 Token Plan 用量上限

  minimax/MiniMax-M2.5: rate_limit_error 2056 已达到 Token Plan 用量上限
```
→ **实际是故障 M，不是故障 K**。预判基于「上次是什么故障」的惯性，而非「这次会是什么故障」。

**本周沉淀的两条判定铁律**：

**铁律一：故障 M vs 故障 K 判定分水岭（TOOLS.md 10/22 10:00 固化）**

| 判据 | 故障 K（MES token 失效） | 故障 M（Token Plan rate_limit） |
|------|--------------------------|-------------------------------|
| `errorReason` | 无（工具层失败） | `rate_limit` ⚡ |
| error 文本 | 含 `mes auth` / `mes_summary_t23.json` | 含 `2056` / `Token Plan 用量上限` / `All models failed` |
| 独立验证 | `mes auth status` → Not logged in | 不影响 MES 登录态 |
| 是否需爸爸 | ✅ 必须 `mes auth login` | ❌ 不需要，等配额自动恢复 |
| 修复动作 | 无（等爸爸） | 不手动补发 / 不 enable |

**判定流程（顺序不可颠倒）**：
1. 先看 `errorReason`：`rate_limit` → **故障 M**；否则看第 2 步
2. 看 error 文本：含 `mes auth` / `mes_summary_t23.json` → **故障 K**
3. 都不含 → 工具调用链异常 → 故障 Q/S

**铁律二：同一 cron 相邻两天可能是完全不同的故障** —— 判定必须基于**当次** errorReason + error 文本，**禁止跨轮次沿用故障标签**（10/22 10:00 固化，10/22 17:00 第二次实证确认）。

**周末全 fail 后的实况印证**（10/23-10/25 连续 3 天三 cron 全 fail）：
```

f730b7b4  10/23 08:01/08:02/08:03/08:09 ×4, 10/24, 10/25 → 全 model_not_found(内含 rate_limit)
```

→ 同一个 cron 在 10/21（故障 K 语义）、10/22（故障 M）、10/23-10/25（故障 M 持续）之间切换，
**若沿用上一轮标签必然判错**。

### 5️⃣ 瞬时抖动排除规则 + 跨日归属规则固化 ⚡⚡

- 同一 cron 在**同一小时内出现成功重跑**（`status=ok` + `delivered=true`）→ 该小时内先前的 error/timeout **不计为独立故障**，归类为「瞬时平台抖动」

**timeout 变种归族**（均属 LLM 层，非工具层）：
