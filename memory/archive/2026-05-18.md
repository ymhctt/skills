**Connect_Timeout**
这个比较好理解，字面上看意思是连接超时。"The number of seconds that the mysqld server waits for a connect packet before responding with Bad handshake"。

MySQL连接一次连接需求经过6次“握手”方可成功，任意一次“握手”失败都有可能导致连接失败，如下图所示。

**wait_timeout**
等待超时，那mysql等什么呢？确切的说是mysql在等用户的请求(query)，如果发现一个线程已经sleep的时间超过wait_timeout了那么这个线程将被清理掉，无论是交换模式或者是非交换模式都以此值为准。

## 📄 MySQL binlog中事务隔离级不一样.md

- 问题现象：

  ​	在协助客户排查生产环境一个死锁问题时，分析死锁信息发现死锁原因是两个事务的行锁（lock_mode X locks rec but not gap）和Next-key 锁（lock_mode X）竞争导致。并通过Next-key 锁的出现，判断该实例默认隔离级是RR。

  ​	但客户一直坚持事务隔离级是RC，并由此不认可我方提供的死锁分析。因为RC隔离级不会存在Next-key 锁，并且在RC隔离级中，SQL执行过程中加上的行锁在该SQL执行完成后，就会释放不满足条件的行，不需要等到事务提交。也就无法触发客户当时的死锁场景。我们也一脸楞逼。

  ​	继续追问下客户反馈并没有使用`select @@global.transaction_isolation; `去查询默认隔离级，而是通过解析的binlog日志中出现的`/*!50718 SET TRANSACTION ISOLATION LEVEL READ COMMITTED*//*!*/;` 判断当前事务隔离级为RC。如下图所示

  ![image-20210325104025985](MySQL binlog中事务隔离级不一样.assets/image-20210325104025985.png)

  ​	问题这下真相大白了，通过binlog判断的事务隔离级是不准确的，在binlog中增加事务隔离级的设置其实是MySQL在特定情况下的一种优化手段，具体分析如下。

  

- 问题原因
