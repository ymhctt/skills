## 📄 MySQL8.0和8.4的差异.md

差异概览

- LTS定位与支持周期： 8.4 是 8.x 的LTS首发版，遵循更保守的行为变更策略，提供约5年高级支持+3年扩展支持；下一大版本为 9.0 MySQL 8.4 Release Notes , MySQL Releases: Innovation and LTS 。
- 认证插件默认值变更： 8.4 默认不再启用已弃用的 mysql_native_password ，仍以 caching_sha2_password 为主；若需要兼容旧客户端，可用 --mysql-native-password=ON 显式开启 What’s New in 8.4 since 8.0 。
- 权限与管理新增/调整：
  - 新增 FLUSH_PRIVILEGES ，专用于 FLUSH PRIVILEGES ；已有 RELOAD 权限仍可兼容使用并在升级时自动补授 FLUSH_PRIVILEGES （若系统中尚无该权限持有者） Changes in 8.4.0 。
  - GTID标签：引入 TRANSACTION_GTID_TAG 权限以设置 gtid_executed ；已有 BINLOG_ADMIN 者升级时自动获得该权限 What’s New in 8.4 since 8.0 。
- 外键约束更严：默认要求父表被引用列上有唯一键； restrict_fk_on_non_standard_key=ON 时对非标准键的创建/变更会被拒绝或发出弃用警告；从 8.0 升级到 8.4 时，历史上已存在的此类外键仍被支持，但新 CREATE/ALTER 需调整 Changes in 8.4.0 。
- 语句与功能移除/替代：
  - 移除 FLUSH HOSTS ；改用 TRUNCATE TABLE performance_schema.host_cache 以获得更精细的可观测性 Percona summary 。
  - 移除在 FLOAT/DOUBLE 上使用 AUTO_INCREMENT （8.0仅弃用警告，8.4直接报错） Percona summary 。
- 服务器/存储引擎默认值大幅调优（性能与稳定性取向），部分典型项：
  - innodb_adaptive_hash_index=OFF （原默认 ON ）
  - innodb_change_buffering=none （原默认 all ）
  - innodb_flush_method=O_DIRECT （Linux，若支持；原默认 fsync ）
  - innodb_io_capacity=10000 （原 200 ）
  - innodb_log_buffer_size=64MB （原 16MB ）
  - temptable_max_ram=总内存3%（1–4GB区间） （原固定 1GB ）
  - 以及一系列基于CPU/NUMA/缓冲池的自适应默认值调整
    以上均为8.4默认相对8.0的差异 What’s New in 8.4 since 8.0 。
    兼容性影响

- 客户端认证兼容性：
  - 依赖 mysql_native_password 的老客户端/驱动在 8.4 上会失败；需升级驱动到支持 caching_sha2_password ，或临时开启 mysql_native_password=ON What’s New in 8.4 since 8.0 。
- 外键约束创建/变更：
  - 在 8.4 中，新建或 ALTER 外键必须引用唯一键或完整索引；历史非唯一/部分索引外键仍可存在但会触发弃用路径，后续应按新规范修复 Changes in 8.4.0 。
- 语句变更与移除：
  - 将任何脚本中的 FLUSH HOSTS 替换为 TRUNCATE performance_schema.host_cache ；权限与监控逻辑可能需要同步调整 Percona summary 。
  - AUTO_INCREMENT 不得用于 FLOAT/DOUBLE ，需改为整数类型或移除该属性 Percona summary 。
- 权限模型变化：
  - 运维脚本如显式使用 RELOAD 做 FLUSH PRIVILEGES ，升级后最好改授或检查 FLUSH_PRIVILEGES ；涉及GTID设置的流程需纳入 TRANSACTION_GTID_TAG 权限 Changes in 8.4.0 , What’s New in 8.4 since 8.0 。
- 默认值导致的性能/行为差异：
  - 写入/IO与统计行为可能显著不同（如更高 io_capacity 、 O_DIRECT 、禁用AHI与变更change buffering）；对查询计划和事务吞吐的影响需在预生产进行基准对比 What’s New in 8.4 since 8.0 。
  升级建议

- 升级路径与策略：
  - 直接从 8.0 升级到 8.4 是支持的；LTS系列内功能不再频繁变动，升级后更稳定 MySQL Releases: Innovation and LTS 。
  - 若当前环境（或依赖）仍需 mysql_native_password ，在服务器启动参数或配置文件中临时开启 mysql_native_password=ON ，并规划尽快迁移到 caching_sha2_password What’s New in 8.4 since 8.0 。
- 架构与SQL清理：
  - 审核所有外键，确保被引用列上存在唯一键；对非唯一/部分索引的外键，优先改造（或在过渡期间通过 restrict_fk_on_non_standard_key 与 --skip-restrict-fk-on-non-standard-key 控制，但不建议长期依赖） Changes in 8.4.0 。
  - 搜索并替换脚本/程序中的 FLUSH HOSTS 为 TRUNCATE TABLE performance_schema.host_cache 。
  - 检查所有 AUTO_INCREMENT 定义，确保仅用于整数类型。
- 权限与安全：
  - 为相关运维账户授予 FLUSH_PRIVILEGES 以满足最小权限原则；涉及GTID设置的管道引入或审计 TRANSACTION_GTID_TAG 权限。
  - 注意OpenSSL更新（至3.0.13），若自定义TLS策略或使用老旧库，进行兼容性评估与证书链验收测试 Changes in 8.4.0 。
- 性能回归风险控制：
  - 在预生产环境用真实负载对比 8.0 与 8.4 默认值组合，包括 innodb_* 、 temptable_* 与IO相关参数；必要时按工作负载开启 adaptive_hash_index 或调整 io_capacity 、 flush_method 等。
  - 记录并观察 mysql_upgrade_history （8.4会在数据目录生成/更新），纳入变更管理与回滚计划 What’s New in 8.4 since 8.0 。

## 一、问题概述

MySQL 主从环境下，为**无主键表**添加自增主键（AUTO_INCREMENT）时，可能导致主从数据完全不一致，且这种不一致**极其隐蔽**——增删改查表面上都正常执行，但数据已经错乱。

**官方 Bug**：[bugs.mysql.com/bug.php?id=103084](https://bugs.mysql.com/bug.php?id=103084)

**影响版本**：8.0.23、8.0.42、8.4.6 等多个版本均验证存在问题。

---

## 二、问题重现

### 实验设置

```sql
-- 无主键测试表
create table testtab(a varchar(20));
```

### 操作步骤

**第一步：插入数据（不同会话、不同提交顺序）**

```
session1:
begin;
insert into testtab values('a');  -- 不提交，rowid已生成

session2:
insert into testtab values('b');  -- 自动提交，先写入binlog
commit;
```

**第二步：此时主从数据顺序已经不同**

| 节点 | select * 结果 |
|------|--------------|
| 主库 | a, b（a在前） |
| 从库 | b, a（顺序相反） |
