一、故障摘要

1.1 故障一句话概括

MariaDB 10.3.31 Galera 主库因 MDEV-21010 堆内存破坏触发 use-after-free，进而导致 AHI（自适应哈希索引）锁持锁线程永久不释放，引发 InnoDB 内部三级锁死锁，最终触发 InnoDB watchdog 主动 crash + 二次 SIGABRT，整个过程 20 分钟。

三、相关 Bug 清单（按因果链路排序）

以下 Bug 编号来自 MariaDB JIRA / Galera GitHub Issues。核心原则：根因是 MDEV-21010，其他都是症状级 Bug。

Bug #1：MDEV-21010 堆内存破坏（根因 Bug）⭐⭐⭐⭐⭐【核心】

MDEV-21010：Mariadb hangs (during a backtrace), stops responding to new connections

jira 链接：https://jira.mariadb.org/browse/MDEV-21010

现象：

mysqld got signal 6 ;
corrupted size vs. prev_size

核心症状：
- TCP listener 保持活动
- socket 保持活动
- 不再接受新查询
- 进程挂死（hang）
- 只能 kill -9 解决

报告中的关键证据：
- MariaDB 10.3.17 触发
- mysqldump 备份期间触发
- max_used_connections=6（低并发也能触发）
- max_threads=65546（典型配置错误共存）

这次故障中的对应证据：
- 21:37:15 出现完全相同的 corrupted size vs. prev_size
- 21:37 起 Aborted connection 爆发
- 21:43:59 0 writes/s、0 fsyncs
- 21:55:30 InnoDB 主动 crash（无法 kill -9 是因为 watchdog 更快）

触发机制：

// 内部内存路径（推测）
mem_heap_free_block(mem_heap_t* heap, ...) {
    // 传入的 heap 已经被错误释放过
    // → 触发 corrupted size vs. prev_size
    // → 触发 SIGABRT
}

或：

// AHI 哈希表内部
hash_table_free(hash_table_t* table) {
    // 已经被部分释放，再次释放
    // → double-free
}

或：

// buf_block_free 路径
buf_block_free(buf_block_t* block) {
    // 释放后某个指针仍然被访问
    // → use-after-free
}

影响版本：MariaDB 10.3.0 - 10.3.38（推测 10.3.39+ 修复）

为什么 MDEV-21010 是根因：
- 错误签名 corrupted size vs. prev_size 完全一致
- 触发的 hang 行为完全一致（TCP 活但 SQL 死）
- 这次故障的 21:37:15 是最早的异常事件
- 后续所有症状（AHI 锁持锁、关闭路径 thd=0x0）都是它的衍生结果

确认方法：
- 登录 MariaDB JIRA 查询 MDEV-21010 的 release notes
- 查看 10.3.39+ / 10.5.x 的 changelog 是否有引用

Bug #2：MDEV-25992 InnoDB 哈希表 use-after-free（传导 Bug）⭐⭐⭐⭐⭐

MDEV-25992 / MDEV-27653 / MDEV-28823

jira 链接：https://jira.mariadb.org/browse/MDEV-25992

现象：

四、根因分析（精确 MDEV-21010 关联）

4.1 故障本质（一句话）

MDEV-21010 触发堆内存破坏 → AHI 哈希表被破坏（use-after-free）→ AHI 锁持锁线程进入死状态 → InnoDB 内部锁三级死锁 → HA 探测只看端口 → 20 分钟"假死" → InnoDB watchdog 主动 crash → 窗口 22.5 分钟。

4.2 故障链路（5 层）

[1] 根因：MDEV-21010 堆内存破坏（21:37:15 之前就发生）
   └─ malloc(): corrupted size vs. prev_size
   └─ 触发位置：InnoDB 内部 mem_heap 路径
   └─ 触发场景：业务高峰 + 资源耗尽
   └─ 触发条件：MDEV-21010 + max_threads 过大

[2] 传导：MDEV-25992 AHI 哈希表被破坏（21:39:27）
   └─ 触发 btr_search_drop_page_hash_when_freed
   └─ thread 139933741364480 拿了 btr_search_latch X 锁
   └─ 持锁线程进入死状态（触发 Bug #3）
   └─ 持锁 919 秒

[3] 蔓延：InnoDB 内部锁三级死锁（21:40:17 - 21:42:01）
   └─ AHI 锁阻塞 → 业务线程在 btr0sea.cc / lock0lock.cc / dict0dict.cc 等待
   └─ LOCK_SYS 锁被持锁线程持锁（377 秒）
   └─ DICT_SYS 锁被持锁线程持锁（273 秒）
   └─ SRV_INNODB_MONITOR 监控线程本身也被卡 636 秒

[4] 监控层/HA 探测误判（21:37-21:55）
   └─ mysqld 进程存活、端口 LISTEN、TCP socket 可建
   └─ 但所有 SQL 全部卡死
   └─ Galera 视图变更（3 节点 → 2 节点）
   └─ 监控把"挂死但存活"误判为"节点正常"
   └─ HA 不切换 → 业务影响 20 分钟

[5] 触发：MDEV-16001 InnoDB 主动 crash + 二次 SIGABRT（21:55:30 - 21:58:12）
   └─ Long semaphore wait > 600s 阈值触发
   └─ InnoDB 主动 srv_shutdown
   └─ 关闭路径卡 12 秒（关闭路径 Bug #4）
   └─ mysqld_safe 重新拉起新进程
   └─ 21:58:12 SST 完成

六、修复建议

6.1 短期：紧急规避（24 小时内）

# /etc/my.cnf 这四行
[mysqld]
# 1. 关闭 AHI — 消除 AHI 锁假死源头
innodb_adaptive_hash_index = OFF

# 2. 合理化线程上限（3002 → 1024）
thread_cache_size = 256
max_connections = 1024

# 3. 防御性参数
innodb_purge_threads = 4
innodb_lock_wait_timeout = 50

效果：
- 立即消除 AHI 锁路径
- 降低内存压力
- 减少锁蔓延窗口

6.2 中期：修复 MDEV-21010 升级（1-2 周内）

强制升级路径：

MariaDB 10.3.31 → 10.3.39+（保守）
                或 → 10.5.x LTS（推荐）

为什么必须升级：
- 关闭 AHI 只是 workaround，不修复根因
- MDEV-21010 在内存分配器深处，subtle 路径众多
- 只有官方修复版才能根本解决

升级风险：
- 10.3 → 10.5 跨大版本，规划灰度
- galera 库版本需协同
- 配置文件项可能有 deprecation

推荐方案：
1. 保守路线：10.3.31 → 10.3.39（最小改动）
2. 推荐路线：10.3.31 → 10.5.12+ LTS（长期支持）

验证修复状态：

# 检查目标版本 release notes 是否引用 MDEV-21010
curl -s https://mariadb.com/kb/en/mariadb-10-3-39-release-notes/ | grep -i "MDEV-21010"
curl -s https://mariadb.com/kb/en/mariadb-10-5-12-release-notes/ | grep -i "MDEV-21010"

6.3 长期：HA 端改造（1-2 月内）

当前问题：
- HA 只探测端口存活 → 误判 20 分钟
- 监控只会"看进程在 = 节点正常"

改造方案：

# 监控侧 — 不依赖端口存活
- 业务 SQL 探测（INNODB_TRX / wsrep_ready）
- 客户端 connect_timeout ≤ 2s
- 客户端 read_timeout ≤ 2s
- 不依赖 zCloud 自动切换 / ProxySQL mysql_*_hostgroup

# wsrep 监控阈值
- wsrep_ready != ON 超过 10s → 主动切
- wsrep_local_state_comment != Synced 超过 10s → 主动切
- 文件描述符 / 长事务 / 长锁等待 → 主动告警

HA 选型建议：
- 主选：业务 SQL 探测（最早发现假死）
- 备选：客户端连接超时（业务侧感知）
- 兜底：Galera 集群视图（被动）

6.4 监控增强

# 必加监控项
- 监控 wsrep_ready / wsrep_local_state_comment
- 监控 InnoDB History List Length（长 list 预警）
- 监控 innodb_rows_inserted/updated（流量基线）
- 监控客户端连接延迟 P99
- 监控 AHI lock waits 数量
- 监控内存和最大线程数
- 监控 mysqld 进程状态（hang 检查）
- 监控 corrupted size vs. prev_size 错误（**MDEV-21010 早期信号**）
- 监控 SIGABRT 触发次数
- 监控 thread pointer: 0x0 关闭路径 bug

# 配 systemd-coredump

6.6 取证核心配置（必须改）

# /etc/my.cnf
[mysqld]
core_file = ON          # 让 mysqld 能写 core

# /etc/sysctl.d/99-coredump.conf
kernel.core_pattern = |/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h %e
kernel.core_uses_pid = 1

# bash
ulimit -c unlimited

效果：
- mysqld hang 时触发 SIGABRT
- 进程不会卡死（systemd-coredump 是 pipe 模式）
- 核心 dump 异步转储
- 可用 coredumpctl list mysqld 取现场

七、长期改进建议

7.1 运维层面

  1. 建立 MariaDB upgrade 流程：每 6 个月评估一次升级
  2. 建立配置文件 review SOP：避免 max_threads=3002 这种灾难配置
  3. 建立 HA 端的"业务 SQL 探测"基线：所有生产 HA 改造必须加业务探针
  4. 建立"mysqld hang"应急 SOP：12 秒关闭路径卡死的应对流程

7.2 数据库层面

  1. AHI 状态监控：定期 SHOW ENGINE INNODB STATUS 检查 AHI 锁路径
  2. 禁用 AHI 作为兜底：高竞争环境关 AHI
  3. 修复 MDEV-21010 路径：升级到 10.3.39+ / 10.5.x LTS
  4. 解案例库：把这次故障写入故障库，定期演练

7.3 业务层面

  1. 客户端 timeout 强制 ≤ 5s：避免等待 60s+ 的延迟累积
  2. 业务层重试机制：所有 MySQL 连接器配置 retry
  3. 业务降级预案：数据库完全不可用时怎么办

7.4 Bug 跟踪层面

  1. 订阅 MariaDB release notes：定期 review "Critical Bug Fixes"
  2. 跟踪 MDEV-21010 状态：确认 10.3.39+ / 10.5.x 是否已修复
  3. 跟踪 MDEV-16001 / MDEV-25992 / MDEV-21155：确认附属 Bug 也已修复
  4. 建立 MDEV 升级 Baseline：每个版本引入哪些 MDEV 修复

八、整备性建议

  1. 故障报告：本案例可作为对内培训材料
  2. 应急 SOP：补充 InnoDB watchdog 主动 crash 路径的应急预案
  3. HA 改造提案：公告业务 HA 侧用业务 SQL 探测替代 LX/MP 探测
  4. 升级路线：制定 MariaDB 10.3.31 → 10.3.39+ / 10.5+ 的升级计划
  5. 配置基线：建立 max_connections / max_threads / innodb_buffer_pool_size 的标准化配置

九、对原文档的修正对照

原文档误判为"corrupt 触发 SIGABRT 假死"的几个核心点

原文档说法 实际证据 修正
"corrupt 触发 SIGABRT" 无任何 corrupt 字段 是 MDEV-21010 堆破坏触发
"MariaDB 10.3.31 已知 bug" 部分对，但更具体是 MDEV-21010 MDEV-21010 是根因
"io 阻塞导致 abort 卡死" 不是（0 writes/s 说明写已停） 不是 IO 阻塞
"Galera HA 切换" 没有切换（主库进程没死） HA 没切换，这是大问题
"kill -15 / kill -9 强杀" 实际是 InnoDB watchdog 自己触发 自动完成
"thd=0x0 关闭路径 bug" 正确 MDEV-21155 关闭路径生命周期
"AHI 锁持锁 919s" 正确 MDEV-16001 AHI 锁持锁不释放
"corrupted size vs. prev_size" 正确 MDEV-21010 根因错误
"my.cnf max_threads=3002" 正确 配置放大器
